# Handoff: Golf Tournament Management Console (Pilot MVP)

## Overview
An admin console for golf tournament organizers to run a multi-stage event: register/import players, form groups (by handicap, seeding, manual, or balanced skill), sequence tournament stages (round robin → qualification → brackets), configure round-robin scoring and tiebreakers, generate match-play scorecards, enter scores (hole-by-hole or match-result, including voice dictation), and track live leaderboards, group standings, qualification cutoffs, and bracket progress through to a champion. Includes a lightweight role model (Organizer/full access vs. Player/read-only + score entry) and an invite/notify flow (WhatsApp) to drive registrations.

## About the Design Files
The bundled file (`Golf Tournament Console.dc.html`) is a **design reference** — a working HTML/JS prototype built to validate flows, data model and business rules, not production code to copy verbatim. It runs standalone in a browser (open it directly) so you can click through every screen and inspect exact behavior. The task is to **recreate this design in your target stack** (React/Vue/native/etc. — pick whichever fits the team, since no production codebase exists yet) with a real backend, auth, and persistence layer replacing the in-memory demo state.

## Fidelity
**High-fidelity.** Colors, type, spacing, component styles, and interaction logic (standings math, bracket seeding, hole-by-hole match resolution, etc.) are final/intentional, not placeholder. Copy text/sample data (player names, course names) is illustrative demo content — replace with real data.

## Design System
Visual language: **Nocturne** — a dark, compact interface (near-neutral blue-grey ground `#161826`, text `#e9e9ed`, single accent `#9184d9` blurple used as line/glow not flood), Inter typeface at medium weight, 8px radii, low chroma outside the accent, outlined (not filled) primary buttons, `:focus-visible` accent rings, tonal 100–900 ramps per role (neutral/accent) generated in OKLCH. Full token sheet and component classes are in `_ds/styles.css` (bundled). Recreate using your own design-token approach, but preserve: dark ground, single accent used sparingly, Inter, 8px radii, outlined primary buttons, compact/dense spacing, tabular-nums on all numeric table columns.

## Data Model
Core entities the backend needs to support:

- **Event**: name, dates, format (`match`|`stroke`), course, city, address, registration deadline, field capacity, player-count mode (`registration`-driven vs `manual` fixed target + apply/regroup action).
- **Account**: name, email, role (`admin`/organizer — full access, or `player` — read-only + own score entry). Organizers manage this list (add/remove/change role) on an Access Control screen.
- **Player**: id, name, handicap, seed (ranking), current group, computed record/points (derived, not stored).
- **Signup**: same as player pre-confirmation; has a status of confirmed (fills up to capacity, in seed order) or waitlisted (overflow). CSV import (`name,handicap` columns) and manual single-add both feed this list. Removing a confirmed player promotes the next waitlisted signup automatically.
- **Group**: id, name (A, B, C…), ordered list of player ids. Regenerated by a chosen **formation rule**:
  - *Balanced skill / By handicap*: sort all players by handicap ascending, then **snake-draft** (0,1,2,…,n-1,n-1,…,1,0 pattern) across `groupCount = max(2, round(playerCount/4))` groups so each group gets a comparable spread.
  - *By seeding*: same snake-draft, sorted by seed/rank instead of handicap.
  - *Manual*: groups follow roster order; intended to support organizer drag-and-drop reassignment (prototype does not implement drag; build this properly in production).
- **Stage**: id, ordered position, type (`Round Robin` | `Qualification Stage` | `Single Match Stage` | `Bracket Stage`), description, **completion deadline** (freeform date/time string in the prototype — use a real datetime in prod), and a **carry-forward config**: `carryForwardEnabled` (bool) + `carryForwardPct` (0–100, step 5) — the percentage of a player's accumulated points from the *previous* stage that should carry into this stage's starting total (stage 1 never has this; disabled = start every player at zero for that stage). The prototype demonstrates the config and a worked-example calculation but only models one real round-robin match set — production must actually apply the carried points when computing a stage's live standings once multiple stages have independent match pools.
- **Match**: id, stage id, group id, round number, player A id, player B id, `holes[]` (array of `'A'|'B'|'H'|null` per hole — null = not yet played). All match-play logic derives from this array; see Standings Logic below.
- **Scoring rules** (per event, applied in round-robin stages): win points, tie/halve points, loss points, hole-win-ratio points (points per net hole won — used both as a scoring component and de facto tiebreaker weight), bonus points (flat, per player), and an ordered **tiebreaker list** (default: head-to-head result → holes-won ratio → fewest holes lost → lower handicap) — must be reorderable (prototype shows static order with a drag handle affordance; wire up real reordering in prod).
- **Qualification config**: `qualifyPerGroup` (top N per group advance — selectable 1/2/3).
- **Bracket**: two brackets (Winners, Consolation) each seeded from qualifiers — top half of the combined qualifier list (by overall rank) → Winners, bottom half → Consolation. Single elimination, 8 seeds → Round of 8 → Semifinals → Final, using standard bracket seeding order `[1,8,4,5,3,6,2,7]` pairing so seed 1 plays seed 8, etc. Each match's winner is chosen manually by the organizer (click a name) rather than computed — bracket matches are decided live on the course, not from the hole data.

## Standings Logic (must be reproduced exactly)
For a completed match, given its `holes[]` array:
- `played` = holes with a non-null value; `remaining` = total holes − played; `lead` = holesWonByA − holesWonByB.
- Match is **complete** if either (a) `|lead| > remaining` (closed out early, standard match-play "dormie" logic — result string like `"3&2"`), or (b) all holes played (`remaining == 0`; result `"AS"` if lead is 0, else `"N UP"`).
- Winner = player with positive lead; `lead === 0` at completion = halved match.
- Per player, aggregate across all their group's matches: wins (W), losses (L), halves/ties (T), holes-won (HW), holes-lost (HL), matches played.
- **Points** = `W×winPts + L×lossPts + T×tiePts + HW×holeRatioPts + bonusPts`.
- **Sort/rank** within a group (and overall): points desc → hole differential (`HW − HL`) desc → lower handicap asc. (Production should apply the full configured tiebreaker chain, not just this 3-step default.)
- **Qualification cutoff**: the points value of the last qualifying player per group; displayed both per-group and as an overall "advancing count / total" stat that updates live as scores are entered.

## Match Result Entry — Two Modes
Score Entry supports two interchangeable entry modes per match (organizer or player toggles per session, not persisted per-match):
1. **Hole-by-hole**: a 9-wide grid of hole cells (for 18 holes), each with 3 stacked buttons (A wins / halved / B wins the hole). Tapping toggles that hole's result; tapping the same value again clears it.
2. **Match result**: pick the winner (Player A / Halved / Player B) plus a free-text margin field accepting `"N&M"` (won by N holes with M remaining), `"N UP"` (through 18, won by N), or `"AS"` (all square). On "Apply result," this is converted into an equivalent `holes[]` array (first `lead` holes assigned to the winner, remaining played-holes marked halved, unplayed holes left null) so it feeds the same standings math as hole-by-hole entry. This is a simplification — it does not preserve which specific holes were lost/won along the way, only the net result; if per-hole granularity matters downstream, consider requiring hole-by-hole entry for stats-heavy tournaments and reserve match-result mode for fast, low-stakes recording.

## Voice-to-Text Score Entry
A microphone button next to the match-result margin field uses the browser's **Web Speech API** (`SpeechRecognition`/`webkitSpeechRecognition`, `lang: 'en-US'`, single-shot, no interim results). On a result, the transcript is parsed for:
- Halve/draw keywords (`"halve"`, `"halved"`, `"all square"`, standalone `"as"`) → winner = Halved, margin = "AS".
- Otherwise, presence of either player's first name in the transcript sets the winner.
- Margin patterns: `/(\d+)\s*(?:&|and)\s*(\d+)/` → `"N&M"`; `/(\d+)\s*up/` → `"N UP"`.
Recognized winner/margin populate the same fields as manual entry — the organizer/player can review and correct before hitting Apply. Falls back to an inline error message if the browser doesn't support the API. **Production note**: Web Speech API browser support and accuracy vary; for a real product evaluate a hosted STT API (e.g., for noisy outdoor course conditions) and consider a push-to-talk UX rather than tap-to-toggle.

## Roles & Permissions
- **Organizer/Admin**: full access to every screen — event setup, registration, roster, grouping rules, stage builder (incl. deadlines & carry-forward config), round-robin setup, scoring rules, qualification, bracket manager, scorecard generator, score entry, leaderboard, reports/export, and access control (manage who is organizer vs player).
- **Player**: restricted to Dashboard (read-only stats/current stage/standings), Live Leaderboard (read-only, includes group-wise breakdown), and Score Entry (can record their own match results, hole-by-hole or match-result mode, including voice dictation) — no access to setup/config/admin/export screens. The prototype includes a "Viewing as" role switch in the sidebar for demoing both views live; in production this should instead be driven by real authentication, and the switch removed.
- Access Control screen: table of accounts (name, email, role toggle Organizer/Player) plus an add-account form. This is where an organizer promotes/demotes accounts.

## Registration & Player Count
- Registration is **not a fixed headcount** — organizers can run a pilot with any number of signups. Confirmed players fill up to `event.capacity` in signup order; overflow automatically goes to a **waitlist** and is promoted automatically when a confirmed spot frees up (removal).
- Add players via: (1) manual one-at-a-time form (name + handicap), (2) **CSV import** (two columns: `name,handicap`, optional header row auto-skipped) — available from both the Registration and Roster screens, (3) organizer can instead lock **Manual** player-count mode in Event Setup — set a target number and "Apply": this pads (promoting waitlist first, else creating placeholder `Player N` entries) or trims (moving the excess to the waitlist) the roster to hit that exact number, then regenerates groups.
- Registration screen also surfaces confirmed/waitlisted counts, spots remaining, and status ("Open" / "Full — waitlist active").

## Invite / Notify Flow
A card on the Registration screen lets the organizer broadcast a sign-up invitation:
- Editable message textarea, pre-filled with event name/dates/venue and a live-updating capacity note.
- **"Send via WhatsApp"** button opens `https://wa.me/?text=<url-encoded message>` in a new tab/window — this opens the user's own WhatsApp share sheet (works for both individual contacts and pre-existing groups the user selects there); there is no server-side WhatsApp Business API integration in the prototype.
- **"Copy message"** copies the text to clipboard for pasting into email, SMS, Slack, etc.
- **Production note**: if true group-broadcast automation is required (not just "open my WhatsApp with this text pre-filled"), integrate the WhatsApp Business Platform (Cloud API) or a provider like Twilio for WhatsApp, plus equivalent email/SMS sending — this needs a backend service and does not work purely client-side.

11. **Bracket Manager** — tab switch (Winners/Consolation). Horizontally scrollable round columns (Round of 8 → Semis → Final) of two-slot match cards; clicking a populated slot advances that player and highlights them; rightmost panel shows the champion once decided.

14. **Live Leaderboard** — full sortable-in-spirit table: rank, name, group, played/W/halved/L, hole differential, points; qualifying rows highlighted; a "live" status tag in the header.
15. **Reports / Export** — 4 summary stat cards. Left: list of export types (Full standings CSV, Group results CSV, Bracket sheet PDF, Scorecards PDF) each with an export action (CSV wired to a real client-side download in the prototype; PDF exports are stubs to build). ## Interactions & Behavior
- All numeric table columns use `font-variant-numeric: tabular-nums` for alignment.
- Buttons: outlined primary (accent border, transparent fill, never a solid fill) per the design system; icon-only buttons for row actions.
- Segmented controls (`.seg`/`.seg-opt`, native radio inputs) used throughout for small mutually-exclusive choices (format, entry mode, winner picker, holes/nine, role, qualify-per-group, bracket tab).
- Group standings, leaderboard, qualification, and bracket views are **fully derived/computed on every render** from the underlying match `holes[]` data — there is no separately-stored "standings" entity; recompute standings server-side the same way (or cache/materialize them, invalidated on match update) rather than storing points as a mutable field.
- Editing scoring rules, qualify-per-group, or the group-formation rule instantly recalculates all dependent views (standings, cutoff, bracket seeding) — preserve this reactivity in production (or clearly message when a recompute is needed, e.g. after bracket seeding has been locked/started).
- CSV import and manual signup both trigger a full group/schedule regeneration (`regen()`), since roster changes invalidate existing round-robin schedules — in production, guard this once matches have live/entered scores (don't silently discard entered results).

## State Management (prototype)
Everything lives in one client-side component state object: `players`, `waitlist`, `groups`, `stages`, `scoring`, `matches`, `qualifyPerGroup`, `bracketWinners` (map of `"{bracket}-{round}-{matchIndex}" → winnerPlayerId`), `bracketTab`, `rrGroupId`, `activeMatchId`, `scForm` (scorecard generator inputs), `entryMode`, `resultForm`, `role`, `accounts`, `accountForm`, `signupForm`, `inviteMessage`, `event` (incl. capacity/deadline/player-count mode). None of this persists (no backend) — a real implementation needs a database, auth, and (ideally) real-time sync for live leaderboard/score updates across devices (organizer on desktop, players entering scores on tablets/phones on the course).
