# Audit — 2026-08-12

Eleven exploratory agents audited the app against a suite of ~1400 passing
tests and found roughly 80 defects. **Almost none were in a function that was
individually wrong.** They were in combinations nobody had a test for, in
defaults nobody had exercised, and in guards that were right for the neighbour
and wrong here.

This file exists because those findings lived only in a conversation. Anything
not written down was going to be lost, and the open items below are the ones
that matter most.

**Status key:** `FIXED` (shipped, with a regression test) · `OPEN` (confirmed,
not fixed) · `GAP` (the app cannot express this at all — a build, not a fix)

---

## 1. Security — S1–S4 fixed, S5–S8 OPEN and live in production

The pattern in every one: **right scope, wrong role or wrong state check.**
The structural IDOR test passes cleanly across the whole surface — it found no
unscoped row id anywhere. It cannot see this class at all.

### S1 — A per-event admin can take over the whole club — **FIXED**
`src/app/actions/organization.ts:52`, same fallback at `src/app/actions/settings.ts:133`

```ts
canEdit: membership?.role === "owner" || membership?.role === "admin" ||
         (session.role === "admin" && !membership)
```

`addAccount` (tournament.ts) creates an `Account` row and **never** an
`OrganizationMember`. So a guest organizer granted admin on ONE event has
`session.role === "admin"` with no membership, hence `canEdit` over the entire
organization. Attack: `addOrganizationMember(self, "owner")`, then
`removeOrganizationMember(realOwner)` — every event, the roster, the branding.

`roles.audit.test.ts` asserts one club's rights don't leak *sideways* into
another. Nothing asserts a per-event admin's rights don't leak *upward*.

**Fix with care.** That fallback exists so legitimate owners created by the
backfill aren't locked out of their own tenant. Removing it naively locks real
people out. Needs a way to distinguish "legacy owner without a membership row"
from "guest admin on one event" — probably backfilling memberships first.

**Fixed** by changing what the fallback asks. It read `!membership` — "I am not
a member of this club" — which is true of an attacker. It now reads "this club
has no members at all", which is a fact about the club and cannot be true of a
club being taken from somebody: the attack needs an owner to take it from. A
genuinely ownerless tenant stays administrable by its event organizer, so
nobody is locked out, and the change was safe to make before any data was
touched.

The rule moved to `lib/services/org-access.ts` — `organization.ts` and
`settings.ts` held identical copies, which is how one of them stayed wrong.
`organizationForNewEvent` also stopped creating ownerless clubs: it read
`...(user ? { members: ... } : {})`, so an organizer with no `User` row got an
organization with nobody in it — the app was manufacturing the very state the
fallback was permissive about. It now creates the User and the ownership row
together, the way inviting staff already did.

`scripts/backfill-org-owners.ts` closes the remaining gap: it gives every
ownerless organization the earliest admin of its earliest event as owner.
Reports and writes nothing by default; `--apply` performs it; idempotent. It
deliberately skips a club with no event admin at all rather than inventing one.
Regression tests: `org-access.test.ts` for the rule, and
`org-takeover.audit.test.ts`, which runs the actual attack — seven of its ten
checks fail against the old condition.

### S2 — An approved scorecard can be rewritten by the player who posted it — **FIXED**
`src/app/actions/tournament.ts:1159` (`saveScorecard`)

`certifyScorecard` refuses when `status === "approved"` — *"An approved card is
the committee's, not the marker's, to change."* `saveScorecard` has no such
check and writes only `strokes`, never touching `status`/`approvedBy`.

A player in a self-scoring event overwrites their approved 82 with a 76. The
row still reads `approvedBy: committee@club`. No audit row. The approval now
vouches for numbers the committee never saw. Staff can do it for anyone —
`assertOwnCard` is a no-op for staff.

Compare the match path, which resets `scoreStatus: "pending"` on every edit "so
a correction always goes back through approval".

### S3 — `disputeScorecard` un-approves at player level, unaudited — **FIXED**
`src/app/actions/tournament.ts:2581`

Identical guards to `certifyScorecard` three lines above, minus the
approved-card check. Undoing an approval is what `reopenScorecard` restricts to
`requireAdminEvent`. An assistant can dispute any card in the field.

### S4 — `clearMatch` erases a confirmed match at player level, unaudited — **FIXED**
`src/app/actions/tournament.ts:1112`

Blanks `holes`, `scoreStatus`, `scoredAt`, `confirmedById` with no check that
the match was confirmed. A player who lost 5&2 clears it after their opponent
signed off; result and confirmation both vanish, no audit row. `reopenMatch`
does strictly less and is admin-only *and* logged.

**All three fixed together**, since they are one bug in three places: an action
that writes a card without asking what state the card was already in.
`isCardLocked`/`statusAfterEdit` in `domain/card-approval.ts` are now the one
place that answers it, shared by `saveScorecard`, `disputeScorecard` and
`certifyScorecard`; an edit also retracts a certification it invalidates, while
a *dispute* deliberately survives an edit. `clearMatch` refuses a confirmed
result — reading `effectiveScoreStatus`, so the auto-confirmed case (stored
column still `pending`) is covered — and both it and `disputeScorecard` now
write audit rows. Regression tests drive the real actions against real rows in
`src/lib/__tests__/approved-card.audit.test.ts`; ten of its sixteen checks fail
against the code as it stood. The static guards are in `audit-guards.test.ts`,
the pure rules in `domain/__tests__/card-approval.test.ts`.

Still open here: the rest of the approval family (`certifyScorecard`,
`approveScorecard`, `approveRound`, `reopenScorecard`) still writes no audit
rows.

### S5 — Any player can repoint anyone's match to another course — OPEN
`src/app/actions/courses.ts:264` (`setMatchCourse`)

No membership check. Its sibling `nameMatchVenue` has one, with a comment
describing this exact attack: *"any signed-in player could repoint anyone's
match at another course and silently rescore it against a different stroke
index."* `setMatchCourse` writes the same fields.

### S6 — Three team handicap settings skip `assertUnlocked` — OPEN
`src/app/actions/teams.ts:294, 317, 357`

`setStageAllowance`, `setStageCountBest`, `setStageAllowanceWeights`. Every
other write in the file applies the lock, as does the analogous per-round
scoring config in tournament.ts. An assistant can move every net result in a
completed, locked event.

### S7 — `applySetupProposal` adds rounds to a locked event — OPEN
`src/app/actions/setup-suggest.ts:125` — `addStage` applies `assertUnlocked`; this doesn't.

### S8 — Four guards now read `viewRole` — OPEN, latent
`skins.ts:26`, `card-photo.ts:55`, `draft-message.ts:42`, `setup-suggest.ts:41`

`audit-guards.test.ts:44` exempts `setPreviewAction` on the stated basis that
*"no write guard reads viewRole… If that ever changes, this exemption becomes a
privilege-escalation hole."* Four now do. **Not currently exploitable** —
`setPreviewRole` whitelists only assistant/player, so `viewRole ≤ role` — but
the test's safety argument is now false.

### Also OPEN
- The **rest of the scorecard-approval family** (`certifyScorecard`,
  `approveScorecard`, `approveRound`, `reopenScorecard`) writes **no audit
  rows**, while every match-play counterpart does. Stroke play is the format
  where one person enters three other people's rounds. `disputeScorecard` now
  writes one; the other four do not.
- `clearRoundScores` deletes a whole round's cards, staff-level, unaudited.
- `disputeMatch` (`requireEvent`) lets any participant flip any match to
  disputed. Documented as deliberate; audited; griefing rather than forgery.

### Verified clean
`attendance.ts` (all three), the whole round-code `play.ts` surface,
`auth.ts` pre-auth paths, `tee-sheet.ts`, `commentary.ts`, `series.ts`,
`roster.ts`, `card-photo.ts`, `skins.ts` scoping, and the event-lifecycle
actions (last-admin invariant holds). `play.ts` is the model the rest should
follow.

## 2. Privacy

### P1 — Password reset links written to the log — **FIXED** (`d92c309`)
`src/lib/email.ts` printed the reset URL and the account email unconditionally
when `RESEND_API_KEY` was unset — a supported state. Every reset token in the
club went to the platform log in plaintext for its 15-minute life. Now
development-only.

### P2 — Five log lines still print member email addresses — OPEN
`email.ts:98, 104, 123, 139, 142` on ordinary send failures. Lower severity;
left deliberately for the next pass.

### P3 — Neither public token can be rotated — OPEN
`shareToken` is minted once at event creation, `registrationToken` once on
first open. **No action anywhere regenerates either.** A leaked `/live/<token>`
or `/register/<token>` URL can only be dealt with by switching the feature off
— and per D2 an organizer often can't even do that.

### P4 — Unpublished tee sheet visible to players — OPEN
`src/lib/services/me.ts:86` and `src/app/(app)/entry/page.tsx:402` both call
`parseTeeSheet` with **no `teeSheetPublished` check**. The dashboard gets this
right. A draft draw reaches `/me` and `/entry` the moment it is saved,
defeating the entire publish/draft distinction.

### Verified clean
No personal data anywhere in the tree. `.gitignore` covers `.env*`, `*.db`,
e2e state. The `/live` payload carries no contact fields and no handicap index.
`/live` visibility guard is correct — staff and participants both 404, and
`generateMetadata` withholds the name before the page guard runs.

## 3. Correctness — registration and intake, D1/D2 fixed, the rest OPEN

### D1 — The registration deadline never closes registration. Ever. — **FIXED**
`src/components/EventSetupClient.tsx:114`

`fmtDate` writes `"Jun 1, 2026"`; `deadlinePassed` requires ISO
(`/^\d{4}-\d{2}-\d{2}$/`) and returns `false` for anything else. The public
form stays open indefinitely **while printing the deadline it is ignoring**.
The stage-deadline picker sends ISO correctly, which is what makes this a bug
rather than a design. `registration.test.ts` passes because it only ever feeds
the pure function ISO strings — the defect is entirely on the write side.

**Fixed** by storing the picker's ISO value and formatting for display instead
of the reverse, plus `parseDeadlineIso`/`formatDeadline` in `lib/deadline.ts`.
The parser also reads back the app's own `"Jun 14, 2026"` output, so every
existing tournament's deadline starts being enforced without a migration — and
still refuses to guess at genuine free text like `"Sat 14 Jun"`, which names no
year. It parses by hand rather than through `Date`, which would apply the
server's timezone to a date that has none. `isIsoDate` turned out to be a shape
check only, so `"2026-13-45"` passed it and sorted fine as a string; the parser
range-checks now. The regression test is the round trip — whatever this app
writes into the column, it must read back — plus a source check that the setup
screen stores the date rather than the sentence.

### D2 — Registration cannot be closed once a tournament is live — **FIXED**
`setRegistrationOpen` and `setRegistrationOverride` both call `assertUnlocked`,
which throws for `status live|completed`. `registerForEvent` never consults
`event.status`. With D1, a running or finished tournament keeps taking public
entries and the only escape is unlocking the whole configuration.

**Fixed** in two halves. The lock is gone from both actions — it protects the
*shape* of a tournament (field, draw, schedule) and closing the door is not
that, so requiring an unlocked event took the control away exactly when it was
needed. And `eventStatus` is now a **required** field on `RegistrationInput`,
so both public paths — `registerForEvent` and `openRegistrationView` — refuse a
`completed` tournament above even the organizer's override. Deliberately only
`completed`: a live club league runs for weeks and members join mid-season,
which is what the switch is for now that it can be reached. Making the field
optional would have left the same hole for the next caller.

### D3 — Bulk delete removes rows you didn't select — **FIXED**
`src/components/RegistrationClient.tsx:112`

One `selected` Set is shared by the confirmed / waitlist / pending tables; the
button label counts only the current table. Tick 3 confirmed and 2 waitlist,
click "Delete 2 selected", **all 5 are deleted**. No confirmation.
`removeSignup` hard-deletes the `Player` row, and `Scorecard.playerId` /
`Match.playerAId` are plain String columns with no relation and no cascade — so
mid-event deletion orphans scorecards and matches. The schema documents
`status "withdrawn"` as the intended soft path; **no code sets or reads it.**

**Fixed** in both halves. The delete now takes the rows of the table whose
button was pressed, counts them with the same expression it deletes them with,
and asks first. And `removeSignup` withdraws rather than deletes whenever the
player has a scorecard or a match — `withdrawn` needed no downstream work,
because the field, the standings and every handicap map are built from
`status === "confirmed"`, while `state.players` keeps the row so the matches
they played still carry a name. An entry with no history is still deleted
outright: a signup added by mistake this morning is not a withdrawal.
`removeSignups` reports deleted/withdrawn/missing so the screen can say which
happened. The waitlist promotes on either path — the place is free either way.

### D4 — Plus-handicaps import backwards — **FIXED**
`actions/roster.ts:164`, `actions/tournament.ts:407`

Both use bare `parseFloat`. `parseFloat("+2.4")` → `+2.4`; the correct reading
is `-2.4`, which the public form gets right. Every scratch-and-better player
imports with the wrong sign and is then *given* strokes they should be giving.
`parseFloat` also accepts `"12.4abc"`, `"999"`, `"-500"`, `"1e9"` — none of
which the form permits, and nothing downstream range-checks.

**Fixed** by extracting the form's own reading into `parseHandicapInput` and
using it in both importers and the organizer's manual add. It returns
`source: "none"` for a blank cell, so the roster importer now distinguishes
"no handicap given" from "scratch" — which also means an unreadable cell no
longer writes a 0 over a stored index. That is the same failure D7 describes on
the registration path, still open there: `upsertMember` decides on
`Number.isFinite(handicap)` and never consults `handicapSource`, which is one
condition away from being fixed.

### D5 — The invite message links to the home page, not the form
`RegistrationClient.tsx:170` — `fullMessage` interpolates `registrationLink`
(the bare origin) instead of `registerUrl` (origin + token). WhatsApp, SMS,
native share and "Copy message" all send a URL with no token.

### D6 — `parseCsv` splits inside quoted fields
`src/lib/csv.ts:86` — `csv.split(/\r?\n/)` runs before `splitCsvLine`, so a
newline inside a quoted cell (any Excel export with a Notes or Address column)
breaks the row. The roster importer then creates a member whose **display name
is a real member's email address**.

### D7 — Self-registering without a handicap wipes the stored index
`register.ts:106` → `services/roster.ts:170`. `cleanRegistration` returns
`handicap: 0, handicapSource: "none"` for a blank box; `upsertMember` checks
`Number.isFinite(0)` (true) and never consults `handicapSource`. A member on
the roster at 12.4 who leaves the box blank is overwritten with 0. The CSV path
guards against exactly this; the registration path does not.

### D8 — Reports and `/live` contradict the leaderboard
`reports/page.tsx:15` calls `standingRows` unconditionally; the leaderboard has
four branches ahead of that call (manual, team, skins/nassau/modified
Stableford). `/live/[token]/page.tsx:56` branches only on `needsTeams`.

For a team round Reports ranks the field at gross 0 / thru 0 and exports that
CSV. For a **manual** format it prints a branded "Final standings snapshot"
with an Advancing column — for a format the leaderboard explicitly refuses to
score.

### D9 — CSV formula injection in report exports
`ReportsClient.tsx:7` quotes only on `/[",\n]/`. A player name of
`=HYPERLINK(...)` — accepted by the unauthenticated public form — executes when
the club opens the export in Excel. `\r` is also missing from the escape class.

### Also OPEN
- **D10** the two importers disagree about name columns (`First Name,Last Name`
  works in one, fails in the other); **D11** the entry importer de-duplicates on
  name, dropping a second real "John Smith"; **D12** a published tee sheet is
  never re-validated when the field changes, so a deleted player leaves a
  dangling id and the group prints with three; **D13** a CSV over ~1 MB fails
  silently (Next's default server-action body limit, no try/catch);
  **D14** duplicate recognised header columns read the wrong cell.

## 4. Scoring — the fixed set

All shipped with regression tests in `src/lib/__tests__/match-play-fixes.test.ts`.

| # | What was wrong | Where |
|---|---|---|
| **FIXED** | `applyNine` sliced an 18-hole stroke index onto nine holes without re-ranking, so a player owed five strokes received two. Root cause behind separate defects in match play, stroke play and skins. Also now narrows a round left at the `"full"` default — which was the state of every nine-hole round nobody had touched the dropdown on | `services/course-resolution.ts` |
| **FIXED** | `deriveNetHoles` sized itself from the stroke index, so a nine-hole match was an 18-hole match with nine unplayed. `absLead > remaining` was never true and the match could **never** be completed — live forever, no result, no standings | `domain/match.ts` |
| **FIXED** | `resolveMatch` read only the final state, so a match that ended 3&2 reported "1 UP" when the players carried on — and credited the loser holes won *after* the finish, feeding `holes-won-ratio` and `fewest-holes-lost` | `domain/match.ts` |
| **FIXED** | `marginToHoles` placed the winner's holes first, reconstructing a card that contradicted its own margin | `domain/match.ts` |
| **FIXED** | Bracket winners applied without checking the player was in that match — the plate re-seeds as losers accumulate, so a positional key changes pairing under a stored winner | `domain/bracket.ts` |
| **FIXED** | `generateCutRound` ranked every confirmed entrant: a percent cut sized against 28 rather than the 24 still in, and eliminated players (0 pts, 0 differential) outranked survivors who played and *lost* (negative differential), so they were advanced again | `services/regroup.ts` |
| **FIXED** | The board disagreed with the engine — `advancingIds` had both of the above. Filtered rather than re-ranked, to avoid the intransitive comparator | `services/tournament.ts` |
| **FIXED** | `flightCountFor` floored at two flights without checking there were two players: **two entrants became two flights of one and ZERO matches, silently** | `domain/grouping.ts` |
| **FIXED** | A forfeit left `holes` null, so every "is this round finished" test read it as unplayed and `currentRoundIndex` froze the tournament on that round | `services/tournament.ts` (`matchSettled`) |

### Still OPEN in scoring

- **The ranking comparator is not a total order.** `head-to-head` is
  intransitive, so `Array.sort` returns a different order depending on which
  *other* players are in the array. Two players level on points where P8 beat
  P9: ranked over 24, P8 is ahead; over 28, **P9 is**. `standings.ts:277`.
- **`head-to-head` and `toughest-N` both reverse a forfeit** — they read the
  raw card, so a conceder is reported as winning the meeting, and holes the
  forfeit discarded still count. `standings.ts:175, 202`.
- **A team forfeit stores and does nothing** — `forfeitMatch` accepts a team id
  but `aggregateStats` compares only `playerAId`/`playerBId`, which a team
  round leaves empty.
- **Impossible margins accepted.** `applyMatchResult` checks only
  `lead <= toPlay` and `lead > total`. `9&8` over nine holes passes both and
  produces a match that can never complete. Correct constraint:
  `N ∈ {M+1, M+2}` and `total − M ≥ N`; "N UP" maxes at 2.
- **A mathematically decided match with one blank hole never completes** — a
  narrow regression from the closeout scan, conservative but real.
- **`MatchResolution.played` changed meaning** — now counts to the closeout, so
  a 3&2 played to 18 reports 16. No consumer breaks today.
- `regroup.ts`'s `scoredMatchCount` still reads holes, so regenerating flights
  can silently discard a forfeit.

### The stroke-play criticals — the `loadEventState` block **FIXED**, the rest OPEN
`loadEventState` queries `scorecard.findMany({ where: { eventId } })` — **no
stageId filter** — and takes the unit from `activeStage`. One block causes:
all rounds summed into one column labelled with the last round's unit; a
**hand-scored round ranked** whenever mixed with a scored one; `Stage.courseId`
ignored (`courseForRound` has **zero production callers**, so multi-course
tournaments score every round against round 1's card); and a **gross round
ranked by net**.

**Fixed**, all four. The board now sums only the rounds that measure what the
active round measures (`carryUnitsCompatible`, the rule the match-play carry
already used) and never a hand-scored one (`isManualFormat`, the check the
weekly view already made). A gross round ranks by gross — a scratch
competition ranked by net is a different competition, and the board was
silently running it. `aggregateStroke` takes a `courseFor(stageId)` instead of
one par/stroke-index pair, so a round played at another club is scored against
that club's card, narrowed to the nine actually played; `courseForRound` has a
production caller at last. `EventState` gained `strokeUnit` and `strokeRounds`
so a screen can say what it is showing rather than assume.

Tests: `domain/__tests__/stroke-agg.test.ts` for the arithmetic (including the
front-nine case, where the same nine scores are four shots apart in net
depending only on which course's stroke index they were allocated from), and
`stroke-board.audit.test.ts` driving the real loader — starting at a field of
one.

Also open: the entry card computes its net total from the raw Handicap Index
while the dots beside it use the Course Handicap — five shots apart on one
screen; the Modified Stableford board allocates with no allowance; and a cut
between two stroke rounds is taken from the running total rather than the round
it cuts out of.

### Money games
**The arithmetic is sound** — 3,000 randomized weeks all balanced to the cent,
every settlement left players square, and no payment rail exists anywhere. The
"records money, never moves it" principle holds.

OPEN: the front/back pot slices an 18-hole index to nine values then allocates
on a **9-hole base**, so a 9-handicapper gets a stroke on all nine holes
instead of five — in a Thursday-night game every hole halves and the pot
refunds. The pot also uses `Player.handicap` (an Index) as a Course Handicap.
And the season table claims to be snapshotted but recomputes live, so
correcting a May scorecard in October rewrites money that changed hands in cash.

GAP: `@@unique([stageId, net])` allows only two pots per round, so a shotgun
with front, back and 18-hole entrants **cannot be represented**.

## 5. Capability gaps — builds, not fixes

- **No third-place match anywhere.** `buildBracket` emits `log2(size)` rounds
  ending in one Final. The word appears nowhere in the codebase. A championship
  run in this app can produce two placings, not six.
- **No losers'-bracket seeding from a standalone round.** `drawBrackets` knows
  `single`/`split`/`plate`; `plate`'s second field comes from
  `firstRoundLosers` of the **main bracket's own** opening round. Nothing
  accepts an externally supplied winner/loser list. The 28-player shape's
  round 3 (16 players, 8 matches, winners→A, losers→B) is only expressible by
  making it the Round of 16 *inside* the main bracket — which costs it being a
  scored round.
- **Exactly two brackets, hard-coded** (`BracketKind = "winners" | "consolation"`).
- **`generateCutRound` cannot draw a cut round as single matches.** As a Round
  Robin it forces flights (16 survivors → 56 matches; single-flight → 120). As
  a Single Match Stage it writes stroke scorecards.
- **`Single Match Stage` has no engine** — `generatesPairings: false`, no code
  path creates its match, and it is offered in the picker.
- **Stroke play has no tiebreak at all.** Two players on 72/72 finish 1st and
  2nd by **seed order** — no countback, no shared position, no notice. The
  Committee Procedures want a play-off for the win and matching cards below it.
  There is also no way to record "play another round to break the tie".
- **A forfeit cannot be recorded in a bracket** — bracket stages have no
  `Match` rows.
- Neither `forfeitMatch` nor `playPts` has an organizer control.
- **`cloneEvent` drops 8 fields its own allowlist requires** — `shape`,
  `sideStyle`, `bracketMode`, `maxPerMatch`, `matchTiebreakers`, `attestBy`,
  `attendanceMode`, `courseMode`, plus `cutScope`, `handicapAllowance`,
  `allowanceWeights`, `countBest`, `playPts`. `clone.test.ts` asserts the
  *policy list* and never that `cloneEvent` obeys it.
- **No club timezone.** `todayIso` reads the server clock; on Vercel (UTC) a US
  club's Tuesday-evening round rolls to Wednesday — sign-up closes hours early
  and tonight's round files under "Earlier rounds".
- **League order of merit** ranks by cumulative net strokes, so a player who
  turns up once and shoots 90 beats three level-par rounds. Needs a rule
  (best-N, minimum-to-qualify); `series.ts` has the vocabulary but is wired for
  cross-tournament use.

## 6. The lesson worth keeping

Three classes of test gave false assurance:

1. **`clone.test.ts`** asserts a policy list, never that the implementation
   obeys it.
2. **`nine-hole-index.test.ts`** passes only because its fixture is already a
   1..9 array — the one layout that hides the bug.
3. **`clone.test.ts`'s regex** used `\n}\n` against a repo with
   `core.autocrlf=true`, so it silently matched nothing and three security
   tests reported "cloneEvent not found" while the function sat right there.

And two fixtures encoded **matches that cannot happen** — `H("AAAAABBBB")` is A
five up with four to play, so the match ended 5&4 and B cannot then win four
holes. An independent agent re-derived both and agreed.

The standing answer is `src/lib/__tests__/matrix.test.ts` and the rules in
`CLAUDE.md`: sweep the cross product, start field sizes at **one**, assert
against the Rules of Golf with the citation, derive the layout route list from
the filesystem, and prefer making the wrong thing unrepresentable over
documenting that callers must remember to check.

> A guard you must remember to call is a guard that will be forgotten.
