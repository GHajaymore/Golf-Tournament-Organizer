## The product in one paragraph

TourneyHQ — golf tournament management for clubs. Next.js 15 (App Router) · React 19 ·
TypeScript · Prisma 6 · PostgreSQL, deployed on Vercel (`main` → `tourneyhq.club`), also
packaged for iOS/Android (Capacitor) and desktop (Electron). It calculates and records money
(skins, payouts, prize splits) but **never moves money** — no payment rails. Pricing tiers
are decided and shipped: Free $0 (10 players, 1 seat, 1 event), Season $49/mo (50 players,
3 seats, unlimited events), Club $175/mo (unlimited, 10 seats); enforcement is **off by
default** and owner-adjustable from `/owner`. Pro/Association tiers are parked.

## What THIS PR does — the capacity over-cap race

**The bug.** Both self-service sign-up paths — `enter.ts` (a signed-in member) and
`register.ts` (a stranger on a public link) — did: count the confirmed field → ask
`decideIntake` confirmed-or-waitlisted → create the row, with nothing between the three
statements. Two people entering a field with one place left at the same instant both read the
same count under `READ COMMITTED` (neither row committed yet), `decideIntake` tells both
"confirmed", and both are created — the field goes over the organizer's (or the tier's) cap.
The same gap let one person's simultaneous double-submit create two rows.

**The fix.** A new helper `src/lib/services/intake-lock.ts`:

```ts
withEventIntakeLock(eventId, (tx) => …)  // pg_advisory_xact_lock(hashtext(eventId)) in a tx
```

serialises the count→decide→create section **per event**. Same-event callers queue (so the
second's count already includes the first); different-event callers never contend; the lock
releases on commit/rollback (the `_xact_` variant, which is also correct under transaction-mode
connection pooling). It takes the seed assignment with it, so concurrent entrants can't collide
on a seed either.

- `enter.ts` — the member lookup and tee resolution stay **outside** the lock (they don't read
  the count); count + decide + seed + create are inside on `tx`.
- `register.ts` — subtler, because `upsertMember` (the roster write-through) returns the
  `memberId` the create needs, uses the global `prisma` client, and **must not run inside the
  transaction** (taking a second pooled connection while entrants are queued on the lock could
  deadlock the pool). The key insight: `decideIntake`'s **accept/reject** verdict never depends
  on the count (a full field *waitlists*, it is never refused) — only the confirmed-vs-waitlisted
  **status** does. So the accept gate + `upsertMember` run outside the lock (race-free), and only
  the fresh re-count + status + create run inside.

**Tests** (both in the audit config — real DB):
- `src/lib/__tests__/intake-lock.audit.test.ts` — the deterministic, mutation-proof guard:
  while one caller holds the lock a second on the same event **blocks** (order pinned exactly),
  and two different events run at once (the control against a global mutex). Verified red when
  the `pg_advisory_xact_lock` line is removed.
- `src/lib/__tests__/intake-capacity-race.audit.test.ts` — an end-to-end integration anchor:
  two real `registerForEvent` calls at one cap-1 link yield exactly one confirmed + one
  waitlisted. Note it is **not** relied on as the mutation guard: whether the two critical
  sections overlap in a given run is a matter of scheduling, so it can pass even without the
  lock on a fast machine. The mechanism test above is the guard that fails when the lock goes.

**Known, deliberate scope gap.** The organizer **bulk-add** (`addFromRoster` in
`src/app/actions/roster.ts`, ~line 462) also does count-then-create in a loop, but it is a
single deliberate organizer action (not "two strangers at once"), it calls `syncPlayerAccount`
per player (a second connection, so the same deadlock concern as `upsertMember`), and it loops
up to ~40 members. Wrapping it correctly (batch the creates in the lock, keep account syncs
outside) is a larger, riskier change than its low concurrency warrants. Left for a focused
follow-up; noted here so it isn't mistaken for an oversight.

## Gotchas that will cost you an hour each if you don't know them

- **This machine: the Bash tool is broken** — it dumps `declare -x` env vars instead of running
  the command. Use **PowerShell** for shell, and the **Read/Grep/Glob/Edit** tools for files.
- **Never write a source file through PowerShell** (`Set-Content`/`Get-Content -Raw` round-trips
  corrupt em-dashes/curly quotes into mojibake, invisibly — it has burned this repo repeatedly).
  Use the **Edit/Write tools**. Anything with a backslash goes through Edit/Write, never a
  heredoc or `node -e`. `git diff --stat` showing a one-line change as seventy is the tell.
- **The full gate** (run before committing anything non-trivial):
  ```
  npx tsc --noEmit && npx vitest run && npx next lint && NEXT_DIST_DIR=.next-ci npx next build
  ```
  plus, for anything touching money / handicaps / authz / intake:
  ```
  npx vitest run --config vitest.audit.config.ts
  ```
  Under Git Bash, prepend `PATH="/c/Program Files/nodejs:$PATH"`. Node runs fine from PowerShell
  with `$env:PATH = "C:\Program Files\nodejs;$env:PATH"`.
- **Mutation-verify every new test**: break the thing it covers, watch it go red, put it back.
  A green cell over a fixture that can't express a wrong answer is decoration. (This PR's
  mechanism test was verified red with the lock removed; the black-box race test was explicitly
  found *not* reliably red, which is why the mechanism test exists.)
- **Merges are SHA-pinned.** A green PR is not a green commit. Recipe:
  ```
  head=$(gh pr view "$PR" --json headRefOid -q .headRefOid)
  gh api "repos/GHajaymore/Golf-Tournament-Organizer/commits/$head/check-runs" -q '.check_runs[] | .status + ":" + (.conclusion // "pending")'
  gh pr merge "$PR" --squash --match-head-commit "$head"
  ```
  Then confirm the **Deploy to production** job (it `needs: verify`, runs on push to `main`);
  a green `verify` with a red/cancelled deploy is usually the Vercel token, the prod DB, the
  100/day deploy allowance, or a 20-min `Completing…` timeout where Vercel actually shipped —
  CLAUDE.md has the full decision tree.
- **CI flakes that are NOT your change** (re-run the same commit / `gh run rerun <id> --failed`):
  a Chromium SEGV in `organizer.spec` desktop; a React "Client Manifest" miss on some client
  component (the named component is noise); a `next/font` fetch failure; an `offline.spec:245`
  scroll race. All documented at length in CLAUDE.md. Read *which* failure it is before editing
  app code — several announce themselves as your bug and are not.
- **Dev database only.** `localhost/tourneyhq_dev` holds demo data; production is full of real
  members. Never seed/test/write against production. The seed and screen-walk scripts refuse a
  non-localhost host on purpose.

## The seeded club — how to look at real screens

`node --env-file=.env scripts/seed-club.mjs` (and `scripts/look-at-screens.mjs`) build a whole
club locally and print cookies to paste in. Walking its permutations as a player has found bugs
that thousands of unit tests passed. Confirm **which session the browser holds** before
believing a screen is wrong about you (`ng_active_event` is HttpOnly; a stale cookie outranks a
fresh one) — that trap has cost real time.
