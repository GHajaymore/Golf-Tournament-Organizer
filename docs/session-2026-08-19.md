## StagesClient — read end to end, six findings

Read all 1568 lines rather than grepping, because the two known findings are
about *depth*, which grep cannot see. The headings grep would have found one of
the six (F2). The other five needed the file.

### F1. "What this round decides" is buried inside "Customize this round"

The walkthrough finding, now located precisely. Three per-type settings sit in
a `SettingsGroup` titled "What this round decides", which is inside the
`customizeOpen` panel, which is inside the `expanded` round:

- **The match** — the Single Match Stage's pairing rule
- **Third and fourth** — the play-off toggle on a Bracket Stage
- **Qualification cut** — how many advance from a Qualification Stage

None of these is a *customization*. They are the reason the round type exists:
a Single Match Stage with no rule set is not a customized round, it is an
unconfigured one, and its picker reads "No pairing set" where nobody can see it.
A Qualification Stage's entire job is the number in that group.

Confirmed at the markup level, not only by reading: `customizeOpen` defaults to
`carryForwardPrompt(...).ask`, which is false for a bracket or a single match,
so **these controls are not in the rendered HTML at all** until two clicks in.

### F2. "Cut line &amp; carry-forward — before the next round" — the ampersand tell

One heading over **three** different things, and it names only two of them:

1. whether points carry forward into the next round,
2. the cut line,
3. **the Generate / Regenerate pairings button** — an action, not a setting.

Nobody looking for "how do I draw Round 2's matches" would look under a heading
about cut lines. The three controls each label themselves, so the heading is the
whole problem: it must name the handover without listing two of its three parts.

### F3. "On the day" holds one control and its blurb describes a control that
isn't in it

    <SettingsGroup title="On the day"
      blurb="When this round is played and whether scores can still go in.">
      <SectionLabel>Scoring window</SectionLabel>
      <p>Whether scores can still be entered for this round.</p>

Two faults at once. **The heading and the label say the same thing twice** —
exactly the trap `simplification-pass.md` records this pass creating on its own
first screen, sitting here already. And **"When this round is played" is not in
this group**: the `Played on` date is up in the header row, so the blurb
advertises something the group does not contain.

### F4. A drifted comment — the fossil of F3

Above the scoring window:

> *Directly under the date, because it is the thing that overrules it.*

It is not directly under the date. The Completion deadline field is four
sections and a group boundary away, on the other side of the "On the day"
heading. Same shape as the drifted comment found in `PlaySettings` yesterday:
something was inserted between a comment and the thing it explained.

### F5. The Tiebreakers blurb asserts two questions where a stroke round has one

    blurb="Set once and rarely touched. Two separate questions — the numbers
           say which is which."

The numbering is conditional on `format === "Match Play"` (only then does the
"1." / "2." prefix appear), but the blurb is not. A Round Robin scored as
Stroke Play shows **one** question and **no numbers**, under a heading promising
two of each.

### F6. The closed round row never says what the round decides

`summaryParts` covers the deadline, the scoring basis, the qualification cut and
the cut/carry transition. It does not cover the third-place play-off or the
single-match pairing. So a Bracket Stage with a play-off switched on and a
Single Match Stage resolving to a real pairing both read **"Standard settings"**
when closed. The most buried settings on the screen are also the only ones the
summary omits.

## The fix

One move, applied five times: **name each thing once, at the level it belongs.**

1. **Lift "What this round decides" out of the Customize panel** to round level,
   beside "Handicaps for &lt;format&gt;", which is already out there for the same
   reason. One click, not two. The per-type settings only — the cut and
   carry-forward stay inside Customize, because they are about the *next* round.
2. **Kept the auto-open of the Customize panel** — considered dropping it and
   did not. It defaults the panel open whenever the carry-forward question is
   unanswered, which reads at first like a band-aid over F1. It is not: the
   carry question is the one setting an organizer cannot afford to miss, the
   transition stays inside the panel, and removing the auto-open would make
   that question *less* visible. A test caught the mistake before the reasoning
   did — "asks the carry-forward question on a points-based chain" renders a
   static markup and depends on the panel being open. Removing a control's only
   route to the screen is exactly the failure this pass is written to avoid.
3. **Rename the ampersand heading** to "Before the next round", with a blurb
   naming all three parts including drawing the round. No nested labels added:
   every control under it already labels itself, and adding headings that repeat
   labels is the documented trap.
4. **Collapse the doubled "On the day" / "Scoring window" heading into one**, and
   **move the Completion deadline into the group** so the drifted comment becomes
   true again. Retitled "When scores are due", which is what both controls
   answer. The sign-up deadline moves below it rather than sitting between the
   two scoring dates.
5. **Make the Tiebreakers blurb conditional** on the format, so it promises two
   questions only where there are two.
6. **Add what the round decides to the closed summary** — the third-place
   play-off and the single-match rule label — and split the summary in two, so
   the Customize button summarizes what is *inside* the panel rather than
   things now visible above it.

Nothing is removed. Every control on the screen before is on it after, which is
what the new render test asserts.

### A third fossil, found by the fix

`RoundDeadlineControl`'s own footer text reads **"Scoring follows the completion
deadline above."** The completion deadline was not above it — it was in a
different section, on the other side of a group heading. Two comments and one
piece of user-facing copy all describing an adjacency that had been broken.
Moving the deadline into the group made all three true again.

## `/choose` — the checklist row that linked to the page it was on

The second walkthrough finding. `OrgSetupChecklist` renders a
**"Create your first tournament"** row whose href is `SETUP_HREF.tournament` =
`/choose?stay=1`. On `/choose` that is the page it is already on — and
`CreateFirstTournament`, the form that actually does it, is fourteen lines
further down the same file. Clicking the row reloads the page under the reader.

Correct on `/dashboard`, where the checklist also mounts and the link is a real
navigation. So the href is not wrong; **the href is wrong *here***.

### The fix is to the link, not to the row

The tempting fix is to drop the step on `/choose`. That would be a removal, and
this pass says removals are usually the wrong change — here demonstrably so:

- it is a real step, and for a brand-new organizer it is the **only** one they
  can currently do (everything else is inside the `(app)` shell, which
  `requireEventSession` bounces them out of);
- it is the `Next` step, so the row carries the "Next" chip;
- dropping it would make the heading count read "0 of 4 done" on one screen and
  "0 of 5 done" on another, for the same organization.

So the row stays and only the link goes. `OrgSetupChecklist` takes a
`currentPath`, and any step whose href resolves to that path renders as a plain
row plus a line saying **"You do this one on this page."** Comparison strips the
query and hash, because `/choose?stay=1` and `/choose` are the same screen — and
`?stay=1` exists precisely to keep this page up.

Generalized rather than special-cased on the tournament step: `/organization`
backs two steps (`profile` and `money`) and the checklist is not mounted there
today, but if it ever is, both would self-link the same way. `currentPath` is
passed at `/dashboard` too, where nothing matches yet — a fact about where the
component is mounted, not a fix aimed at one row.

No wording says "scroll down": the component does not know where on the page it
has been mounted, and a direction it cannot verify is the same class of claim as
the three drifted "above"s found in `StagesClient` this morning.

### K1. Two switches, one word, and they are not opposites

Within a few inches of each other:

- a banner button reading **"Close registration"** / **"Reopen registration"** —
  `setRegistrationOverride`, whether this tournament takes entries at all;
- a card titled **"Open registration"** whose button read **"Open registration"**
  / **"Close sign-ups"** — `setRegistrationOpen`, whether the public
  no-account link exists.

An organizer wanting to stop people signing up had two plausible controls and
nothing on screen to tell them apart. Both switches are real, both work, and
`decideIntake` checks both — so this is not a bug, it is the pass's exact
subject: the name is the whole problem.

The card is now **"Public sign-up link"**, with **"Publish the link"** /

"Invite players" card refuses with *"Open registration first — the sign-up link
doesn't exist until you do."* A refusal pointing at a button that no longer
exists is worse than no refusal, so it now says "Publish the sign-up link
first".

### K2. The copy told organizers the close button was cosmetic

The banner said, when closed:

> **You can still add players below** — closing only changes what this says.

**That is false.** `registrationStatus` with `override: true` returns
`acceptingEntries: false`; `decideIntake` refuses the entry on that alone. So
closing turns away every visitor to the sign-up link. The half that IS true is
that adding somebody by hand still works.

This is the mirror of the defect fixed on 2026-08-18, when a course consequence
was found to be OVERSTATED. Understating one is the same failure: an organizer
closes registration believing it is a label, and wonders why nobody signed up.

### K3. A published link that turns everybody away, silently

The two switches are independent, so `registrationOpen: true` with the
tournament past its deadline is a live, copyable link that refuses every
visitor. The screen showed a working link and a "Closed" chip four inches
apart, with nothing joining them. It now says so, in the card, with the reason.

### Found, NOT fixed — three meanings of "registration is open"

`LifecycleBar` (on `/dashboard`) has a **third** control labelled **"Open
registration"**, which calls `setEventStatus("registration")` — and that neither
publishes the link nor changes what `registrationStatus` decides. So:

1. the lifecycle phase, whose chip reads "Registration open";
2. `registrationOpen`, the public link;
3. `registrationStatus(...).acceptingEntries`, whether entries are taken.

Pressing "Open registration" on the dashboard sets the chip to "Registration
open" and **does not create a sign-up link**.

Renaming this one is a change to the lifecycle vocabulary an organizer learns,
and it wants one decision made across all three — **Ajay's call, not a heading
fix.** The `/registration` rename takes the collisions from three to two and is
safe on its own, because it names exactly what its switch does.

rather than committed; it was referenced by nothing, so it changed no screen.
Nothing of value is lost and the pass branch is one subject again.

## Why parking beat keeping it, recorded so the reasoning survives

1. **The two kinds of change carry different risk, and nothing has been seen.**
   The pass changes headings, refusals and explanations — a wording error is a
   wording fix. The leaderboard changes a table people watch live during a
   competition: tie positions, a cut line, colour. Bundled together, either the
   whole branch waits on a look, or the leaderboard ships without one.
2. **One branch, one subject** — the same reason this pass commits per screen.
3. **The aggregation is bigger than I said.** I called it "one more screen". It
   is not: it feeds the qualification and cut logic, and `services/tournament.ts`
   carries long comments about the board and the engine having already disagreed
   about who advances. That is the COMBINATIONS class `docs/audit-2026-08-12.md`
   exists for — it wants the matrix sweep and a human watching it, not a tidy
   join and a green test run.

## What the leaderboard work found, for whoever picks it up

Worth keeping even though the code is parked.

- `LeaderboardTable` already renders two boards and `StandingRow` already
  carries both sets of fields. Which one you get is decided by **one setting**,
  `event.format === "stroke"`, with no choice anywhere.
- **A match-play event has no stroke data at all.** Every match-play standing row
  hard-codes `gross: 0, net: 0, toPar: 0, thru: 0`
  (`services/tournament.ts:905`), so a to-par board there is a column of zeros.
  This is the real blocker behind the "choice" Ajay asked for.
- The strokes DO exist wherever a full scorecard was entered: `MatchScorecard`,
  one row per side, keyed `(matchId, slot)` with slot `"A" | "B"`.
- **What is missing is the join, not the arithmetic.** Resolve
  `(matchId, slot)` → `(playerId, stageId)` and hand the rows to
  `parseStrokeCards` → `aggregateStroke`, the same pipeline a stroke round uses.
  Allowance, strokes received, par-thru, Stableford and the countback card are
  decided there already, and a second copy of any of them is the drift this
  codebase keeps paying for.
- It must **invent nothing**. A match scored by hole winners has no card and
  contributes no holes — no falling back to par, to the hole result, or to the
  opponent's card. A to-par figure assembled from guesses looks exactly like a
  real one.
- Which means a club that never enters a full card sees an empty board, so it
  needs a coverage figure and a refusal in the established idiom rather than a
  column of dashes.

## `AvailabilityCalendar` — a lint warning that was a real defect

Fourteenth screen, picked precisely because it carried a **pre-existing lint
warning** that had been sitting there long enough to read as a nag:

> `aria-pressed` is not supported by the role `gridcell`.

It is not a nag. The square was one element — `<button role="gridcell">` — and
overriding a button's implicit role takes `aria-pressed` with it, because
`gridcell` does not support the attribute. So on **the one screen whose entire
question is "am I playing on these dates"**, a screen-reader user was told
nothing at all about whether they were in or out.

The fix is the standard grid pattern: the **cell is the container** and the
interactive widget lives inside it, so the button keeps its own role and its
state.

### …and the rows had already been thrown away

Making that legal meant looking at the grid, which turned up the second half:

    {m.weeks.flat().map((day) => <Square … />)}

**The weeks existed in the data and the markup flattened them.** Forty-two cells
as direct children of `role="grid"`, no rows at all — so the structure a
calendar is *for* was gone before anything could read it. `m.weeks` is already
an array of weeks; it now renders as rows.

The weekday initials moved OUT of the grid. They are `aria-hidden` decoration —
every square carries its own date in its accessible name — and a row of nothing
but hidden cells is an empty row to anything reading the structure.

### The trap I nearly walked into

My first version put `display: contents` on the new cell wrapper, which is the
tidy way to keep the button as the grid item. **`display: contents` has a long
history of dropping the element it is on out of the accessibility tree** — so
the fix would have traded a missing `aria-pressed` for a missing `gridcell` and
looked finished. An ordinary flex box with the button stretched to fill it costs
nothing and is not a bet on browser behaviour.

`minWidth: 0` on the button for the reason CLAUDE.md gives: a seven-column month
on a 320px phone needs its children allowed to shrink.

## The last three warnings — and lint is now clean

Having found that one standing warning was a real defect, the other three were
worth the same look rather than the same shrug. All three were real; none was
cosmetic.

### `LoginPanel` — a ternary doing a statement's job

    onSubmit={(e) => { e.preventDefault(); login ? submitLogin() : submitSignup(); }}

Both branches are called for their side effects, and a ternary in that position
reads as though it produces something. `if/else` now. The front door is the last
place to leave a warning standing.

### Two `useMemo`s that never memoized anything

`MoneyClient` and `ScoreEntryClient` both had the same shape:

    const groupIds = round?.groupPlayerIds ?? [];      // new array EVERY render
    const shareIds = useMemo(…, [scope, groupIds, …]); // …so the dep always changed

The `?? []` allocated a fresh array on every render, so the dependency was never
equal to itself and the memo re-ran unconditionally. The warning said exactly
that and had been read as noise.

Both now use a shared module-level empty array with a stable identity. It
matters most in `ScoreEntryClient`, where the memo runs `resolveMatch` on a
screen used **hole by hole, on a phone, on a course** — the one place in the app
where wasted work is felt.

**`next lint` is now completely clean** — zero warnings, from four at the start
of the session. Which is the point: warnings that stand get read as noise, and
then a real one hides among them. Three of these four were real.
