## The gate got 58% faster, measured

The single biggest thing to know about working in this repo today.

| | end to end | first signal on a broken typecheck/lint/test |
|---|---|---|
| before | **9m32s** | ~9m30s |
| after #148 | 7m00s | 2m23s |
| after #149 | **3m58s** | **2m26s** |

`verify` was one sequential job, and the end-to-end run was six of its nine and
a half minutes. Everything else queued behind it for no reason other than being
written in the same list.

It is now `unit`, `build` and three `e2e` legs — one per viewport — running
concurrently, with `verify` surviving as a do-nothing gate that `needs` them
all. **That name is load-bearing:** the branch ruleset requires a check called
exactly `verify` (`context: verify`, integration 15368 — read from
`repos/.../rules/branches/main`, not assumed). Renaming it silently
un-protects `main`.

Three things found while in there:

- **`next lint` had never run in CI at all.** It is in the documented local
  gate, so a lint error only failed for whoever remembered to run it. It caught
  a real one the same day — a `const` used above its own declaration, which
  `tsc` passes and the build refuses.
- The Playwright browser download was not cached. It is now, keyed on the
  resolved `@playwright/test` version rather than the lockfile, which churns on
  every unrelated bump.
- The drift check's own comment said it had to run before the migrations. It
  does not: `prisma migrate diff` replays the migrations folder into the empty
  *shadow* database and never reads the real one.

### What unblocked the viewport split, and the belief that had blocked it

A note in the working memory of previous sessions said running only
`--project=desktop` turns CI red. That is why the three viewports stayed welded
into one 6.5-minute process.

Read properly, the original incident was about **local validation** — a spec
asserted the desktop sidebar, passed on desktop alone, and failed on both
phones. That rule is true and still matters. What was never true is the reading
carried forward: that a single-project *invocation* cannot stand alone.
Measured before relying on it — `--project=desktop`: 78 passed, 12 skipped, 0
failed.

Each leg is now its own `playwright test` with its own PostgreSQL service and
its own seed. `workers: 1` stays, correctly: three of the six spec files write
to the shared fixture, so this parallelises *processes that share nothing*,
never tests that share a database. A side effect worth having — with a database
per leg, a spec's writes can no longer reach another viewport, so the
contamination bug where 3 tests × 3 viewports drove a nine-hole card to eighteen
is now structurally impossible.

`ci-e2e-matrix.test.ts` guards the one silent direction: *renaming* a project
already fails loudly (Playwright errors on an unknown `--project`), but *adding*
one to the config and not to the matrix means the new viewport is never run and
every leg stays green.

## The landing palette is generated now

`page.tsx` carried ~30 colour tokens picked by eye and declared twice. That was
the *cause* of the two contrast failures fixed in #138, not an incidental
detail: it is the one surface `themes.test.ts` cannot reach.

`solveLightness` is lifted out of `lightnessFor` in `themes.ts` — same binary
search, no longer tied to `contrastFloors` — and `landing-palette.ts` drives it.
The hues stay hand-chosen; only the **weights** are solved.

**The structure that fell out of measuring the old palette** is the part worth
remembering. The page has exactly two surfaces, lacquer and cream, and the
appearance flip swaps which is the page and which is the inverted band. The old
values already agreed without anyone noticing: the dark ground's
`--paper-accent` was character-for-character the light ground's `--brass`, and
its `--paper-soft` matched the light `--ink-soft` to one unit of blue. They were
one solve against one surface, written out twice.

Foregrounds solve against the **worst background their surface presents**.
`--ink-faint` cleared 4.73:1 on the dark page and about 4.45 on the feature
card's hover state — the same text one mouse movement later.

Before/after on a real dev server, full page, both grounds: **page height
identical to the pixel, max channel delta 17/255, mean 1.1.**

`landing-contrast.test.ts` gained the check that matters more than the grading:
**`page.tsx` may write no colour of its own except the brand's six**, which stay
hand-written precisely because a logo must not be wired to a solver free to move
it.

## The touch floor was barely enforced

`touch.spec` measured `/dashboard` and nothing else — one screen out of
twenty-three, and an *at-desk* one, the very screen the density assertion beside
it pins at ≤36px.

Nav items now carry a `tier` (`on-course` / `at-desk`), split by **where a
screen is used, not who uses it** — tiering by audience puts Score entry and the
Tee sheet on the desk side because a member of *staff* holds them, when both are
worked standing on a tee box in sun.

The sweep's first run failed on **six of the ten** on-course routes:

| control | was |
|---|---|
| the 18-hole strip on the hole-by-hole card | 30px |
| bracket seat (how a match is advanced) | 33px |
| `field-info-btn` — whose own comment says *"exists for phone users"* | 26px |
| labels wrapping a checkbox | 19px |
| rule citations linking to the USGA and R&A | 17–19px |

The existing coarse-pointer block missed every one because it targets
design-system **classes** — `.btn`, `.input`, `.seg-opt`, `.m-tab` — so anything
built from a bare `<button>` with inline styles was never covered.

**Two of the six were the test being wrong**, and fixing the detector mattered
as much as fixing the CSS: a native checkbox inside a `<label>` is tapped by the
label, and an `<a>` with computed `display: inline` is a word in a sentence. The
rule citations survived both corrections, which is how they were confirmed as
real targets rather than prose.

25 touch assertions now pass across three viewports, up from 2.

**The invariant:** the tier decides *what is asserted, never whether a screen is
swept*. `layout.spec` still walks the filesystem, and `nav-tier.test.ts` asserts
it takes its routes from `readdir` and not from `NAV`.

## A guard that could not fail, and a test satisfied by its own comment

Both found by mutation testing, both in code written the same hour.

- `reorder.ts` had `if (before.size === 0) return []` for the first render.
  Deleting it changed no behaviour and turned no test red — on a first render
  every row is unknown to the previous board, so the new-row rule already
  covered it. Gone. The first-render *test* stays, downgraded in its own
  docblock to a statement of intent rather than an independent guard.
- `ci-e2e-matrix.test.ts` asserted `fail-fast: false` against a `.yml` read with
  `readVerbatim`. Flipping the setting went red only because the edit also
  rewrote the comment above it; a change touching just the setting would have
  sailed through. **`readSource` strips TypeScript comments and knows nothing
  about `#`.** Comments are blanked before assertion now.

## What the leaderboard motion revealed

Recommendation 4 is done, but the interesting part is where it does *not* apply.

Row-reorder motion needs the list to update **in place**, and exactly one page
does: `LiveRefresh` polls and calls `router.refresh()`, and it is mounted only
on `/live/[token]` — the public spectator board.

**The console's "Live leaderboard" did not live-update at all** — no polling, no
refresh, changing only when somebody reloaded. Worse than silent: the page
carried a STATIC badge reading "Updating live" in an accent colour, and the
footnote under the table promised match points "update live as scores are
entered". A screen whose name, badge and footnote all claimed something none of
them did.

**FIXED in the same PR as this document.** The badge is now the component that
actually does it — `LiveRefresh`, the same one the spectator board uses, so the
claim and the polling are one piece of code. It was already built for the
harder case: 30s only while the tab is visible, waking on focus and reconnect,
and reporting age from a SERVER-stamped timestamp so an ageing label is the
failure showing through rather than a client clock ticking over a dead
connection. The battery objection turns out to be answered by the visibility
gate, which is why this was a small change rather than a judgement call.

The console board animates now too, for the same reason the spectator board
does. The FLIP effect became a hook: `FlipList` for the player board's `<ol>`,
`FlipTableBody` for the console's `<tbody>` — a separate component rather than
a prop, because anything between `<table>` and `<tbody>` is hoisted out by the
HTML parser and a `<div>` there silently destroys the layout.

`reorder.test.ts` asserted the opposite of this, and was right to when it was
written. Its assertion is now about the CONDITION rather than the file: a board
that animates must have something behind it that updates it in place, and the
pages rendering one must mount the poller. Take polling off a board and the
motion has to come off with it.

## The icon sprite — DONE, #152 (`7ed5fd3`)

Listed here as open and finished the same day, so this section is what happened
rather than what to do.

**272.6 KB of woff2 became 13.2 KB brotli.** The font carried two weights of
roughly 1,500 glyphs to draw about 120, and it was `font-display: block`, so
every icon in the product was invisible until it arrived. `static/media` went
7.9 MB → 336 KB, with zero Phosphor files in the build.

The previous handoff's rule was "sprite it if under a hundred icons"; the real
figure is 134 across 402 converted call sites, which fails that rule. The
threshold was a guess and the weight is a 95% cut, so the rule was wrong rather
than the recommendation. **Measure the thing the decision actually turns on.**

`<Icon>` is 1em square with `fill: currentColor`, because the thing it replaced
was TEXT — every call site sizes its icon with `fontSize` and a hundred do it
inline, so 402 of them did not have to change. It also still accepts the legacy
`"ph ph-eye"` spelling, because icon names are carried as data (`nav.ts` stores
one on every entry).

### THE FAILURE MODE TO KNOW ABOUT BEFORE TOUCHING ICONS AGAIN

A `<use href="#i-…">` pointing at a symbol that is not in the sprite renders
**nothing**. No error, no console warning, no failed request, no layout shift —
the element keeps its 1em box and draws empty space. The build succeeds, the
page renders, and every other test passes.

It happened FOUR times during the conversion, each through a clean typecheck
and a green suite: `moon` and `circle-half` in the appearance picker, `circle`
on every person chip, and both weights of five player tabs. All four were names
the generator could not SEE — composed at the call site out of fragments
(`` `ph ph-${…}` ``) rather than written out.

So every icon name in the app is a complete literal, enforced rather than
documented, and there are two guards because neither half is enough:

- `icon-sprite.test.ts` — the sprite holds every name the source asks for, and
  no name is assembled at runtime.
- `layout.spec.ts` — on every swept route, every `<use>` resolves to a symbol
  that exists and has a box. **This is the half only a rendered page can see**,
  and it is the one that found all four blanks.

If you add an icon: use a literal name, then run
`node scripts/build-icon-sprite.mjs`. The unit test tells you if you forget.

### The sprite appears TWICE in the HTML, and that is fine

Verified on production after the deploy, and recorded here because it looks
like a bug and is the obvious thing for somebody to "fix":

```
<symbol id="…">                    134   the rendered HTML
<symbol id=…                   134   the same again, escaped, in the
                                          RSC flight payload
```

React serialises anything in the root layout into the flight data as well as
the document, `dangerouslySetInnerHTML` included, so the landing page went from
171 KB to 295 KB uncompressed. That number is alarming and almost entirely
meaningless: the two copies are byte-identical, so the compressor eats the
second one.

Measured on the live page rather than reasoned about:

```
as served, brotli      38.4 KB
one copy only, brotli  37.0 KB
the duplicate costs     1.4 KB      (against 57.9 KB raw)
```

1.4 KB, against the 259 KB the sprite saves. Every way of removing it — an
external `/icons.svg` with `<use href="/icons.svg#…">` being the obvious one —
trades that 1.4 KB for a network request and for external `<use>`, which is the
feature that works until it doesn't. **Leave it alone**, and if the raw
document size is ever the thing being optimised, come back with a measurement
rather than this paragraph.

### It also fixed a bug nobody had noticed

`AvailabilityCalendar` asked for `"ph-check-bold"` and `"ph-x-bold"`, which
read as an icon named `check-bold`. Neither stylesheet the app imported defines
such a class, so two icons in the availability grid had simply been invisible.
A webfont charges ~145 KB per weight, which is why only two were ever imported;
a sprite charges per icon, so bold costs about 450 bytes now and they draw.

WHAT IS LEFT IS SMALL, and worth writing down so the next person does not go
looking for another 272 KB:

- `unminified-css` (scores 50) — **2.4 KB wasted of 5.65 KB**, and it is
  `LANDING_CSS`. Next does not minify a hand-written string handed to
  `dangerouslySetInnerHTML`, so the landing page ships its stylesheet with
  every comment and indent intact. Those comments are load-bearing
  documentation and should not be deleted; minifying at build time is the fix
  if it is ever worth 2.4 KB.
- `legacy-javascript` (0) — **11.7 KB** of polyfills in one Next chunk, for
  things like `Array.prototype.at`. That is the browserslist target, so it is a
  config decision about which browsers to keep, not a bug.
- `render-blocking` (50) — a single 7.6 KB stylesheet.
- LCP at 3.1 s is the one metric still scoring below 90 (72). It is the largest
  remaining lever and it is not an asset problem — there are no third parties
  and the page is 395 KB total.

None of these is worth starting on its own evidence. **Re-measure before
choosing**, and treat this table the way this document asked to be treated
about the icon count: as a reading taken on one day, not a target.

## Traps hit today

- **`git checkout -- <file>` discards uncommitted work.** It cost the same fix
  twice: once on `checklist.ts`, once on an untracked migration that
  `git checkout` could not restore at all. **Commit before mutation testing.**
  The CLAUDE.md instruction to use git rather than a saved copy is right, and it
  only works on committed content.
- **`npm ci`, not `npm install`, in a worktree.** A worktree's `node_modules`
  holds only caches; real deps resolve up to the main checkout, which can be
  missing something `package.json` lists (`@phosphor-icons/web` was, so the dev
  server would not build). `npm install --no-save --no-package-lock` looks
  surgical and is not: it installs everything anyway *and* resolves off version
  ranges rather than the lockfile, which silently produced Playwright 1.63.0
  against the pinned 1.62.1.
- **Building with a novel `NEXT_DIST_DIR` rewrites `tsconfig.json`.** Next adds
  the new `<dir>/types` glob to `include`. That is where the committed
  `.next-playfix` and `.next-pubaudit` entries came from. Revert it or clean up.
- **Backticks in a `git commit -m` message get executed by bash.** Whole clauses
  vanished from a commit message before anyone noticed. Use `-F` and a file.
- Bash heredocs in this environment ate one level of backslashes, which broke a
  regex inside a test. Use the editing tools for anything with escaping in it.
- **A committed script must not shell out to `grep`.** The sprite generator did,
  and worked on the Linux runner and under Git Bash and broke on Windows the
  moment the pattern needed a quote — `execSync` hands the string to cmd.exe,
  which has its own ideas about quoting. It walks the filesystem in Node now. A
  generator that only runs on some of the machines that need it is a generator
  whose output goes stale on the others.
- **A `next start` left running holds its port, and the next one silently serves
  the old build.** Two verification runs were measured against stale output
  before the sprite count (125 vs 134) gave it away. `pkill -f "next start"` did
  not reach them; `Get-NetTCPConnection -LocalPort N` then `Stop-Process` did.
  Check the server is serving what you just built before believing what it says.
- **A truncated `tail` of a CI result is not a CI result.** #151 was reported
  green off the last ten lines while two of its six e2e legs had failed. List
  every check — `gh pr checks N --json name,bucket` — rather than reading the
  end of the output.
