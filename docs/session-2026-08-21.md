## What the spec asked for, in order

1. The join — `MatchScorecard (matchId, slot)` → `(playerId, stageId)`, reusing
   `parseStrokeCards` → `aggregateStroke`. Not a second copy of the arithmetic.
2. Incomplete-card handling on the board: show, do not rank.
3. Format-declared input mode, with an override.
4. The leaderboard choice — parked on `claude/tour-leaderboard`, lands separately.

## Reading first — what is actually there

- `MatchScorecard` is written by `saveMatchScorecard`
  (`src/app/actions/tournament.ts:1389`) and read by exactly one screen,
  `/entry`. Nothing else in the app has ever looked at those strokes. That is
  why a match-play event has no stroke data: the cards exist, nothing joins them.
- `loadEventState` loads `prisma.scorecard` only. `strokeStandings` is built
  from those rows, so a match-play event produces the column of zeros the spec
  describes, and `standingRows` hard-codes `gross: 0, net: 0, toPar: 0, thru: 0`
  for every non-stroke row (`services/tournament.ts:905`).
- `aggregateStroke` already does all the arithmetic — par, allowance, strokes
  received, Stableford points, per-hole cards for the countback.

## The thing the reading changed

**A Round Robin stage holds the WHOLE round robin, not one week of pairings.**
`expectedRrTotal` sums `roundRobinMatchCount(n)` per flight, so in a flight of
four each player has THREE matches inside one stage. The join therefore produces
several cards for the same `(playerId, stageId)` — which `Scorecard`'s
`@@unique([stageId, playerId])` has always made impossible, and which
`aggregateStroke` was not written for: `holesByStage.set(...)` would silently
overwrite, so a countback would read whichever card was queried last.

Two consequences, both handled below rather than papered over:

- The stroke totals for such a stage are the sum of every match the player
  played in it. That arithmetic is coherent — `parThru` and `strokesReceived`
  accumulate per hole played, so to-par and net stay meaningful over 54 holes as
  over 18 — but it only compares fairly between players who have finished all
  their matches. The completeness rule below is what makes that safe.
- A countback cannot read two cards at once. Where a player holds more than one
  card in a round, that round's countback card is emptied, which
  `countbackCompare` already treats as "cannot separate" rather than "loses".

## Decision 1, and the line I did NOT cross

"Complete" means two things and must not be merged. So there are two readers,
and they read different things:

| Question | Reader | Used for |
| --- | --- | --- |
| Is the MATCH settled? | `matchSettled` — unchanged | bracket, standings, round completion, payouts |
| Is the CARD finished? | `resolveMatch(holes).winner !== null` \|\| forfeit | whether the card can still gain holes |
| Is the CARD complete? | every hole of the round returned | whether it is RANKED on the stroke board |

`matchSettled` is untouched. The spec flags whether it should become "has a
winner" as a real open question; using a stricter reading for the *card*
question does not answer it, because nothing about rounds, money or brackets
consults the card reader.

The board rule is one predicate on the aggregate:

    ranked = thru > 0 && !stoppedShort

`stoppedShort` is true when a FINISHED card has holes that were never played.
Three states, each meaning something different:

- complete card → ranked.
- incomplete, not finished → ranked provisionally. This is the ordinary live
  leaderboard, "thru 12", and it must not regress.
- finished, incomplete → shown, not ranked. This is the 5&4 card.

`finished` is set only for match-derived cards. A stroke `Scorecard` is never
marked finished, so ordinary stroke play behaves exactly as it did. Whether an
unreturned card at the end of a completed event should be an NR (Rule 3.3b) is a
separate question nobody has decided, and this leaves it alone deliberately.

## Progress

### 1. The join — DONE

- `src/lib/domain/match-cards.ts` — pure. `matchStrokeCards(cards, matches)`
  resolves `(matchId, slot)` to `(playerId, stageId)`; `matchCardFinished(m)`
  answers the card question off `resolveMatch(...).winner`, guarded against the
  `"[]"` schema default (`resolveMatch([])` reports a halved match over zero
  holes, so an untouched match would otherwise claim to be finished).
- `loadEventState` loads `matchScorecard` alongside `scorecard` and feeds both
  through the SAME `parseStrokeCards` → `aggregateStroke`. No second copy of the
  allowance or the countback. `TeamScorecard` is deliberately not joined.
- `standingRows` no longer hard-codes `gross: 0, net: 0, toPar: 0, thru: 0` on a
  match-play row; it carries whatever the player returned. Their POSITION is
  still their match points.
- `aggregateStroke` taught to cope with several cards on one `(player, stage)`:
  totals add, and that round's countback card is EMPTIED rather than overwritten
  (`countbackCompare` reads an empty card as "cannot separate", which is the
  treatment it already gives an incomplete one).

### 2. Show, do not rank — DONE

- `StrokeAgg` gains `holesOwed` and `stoppedShort`; `isRanked(agg)` is the one
  reader of "does this row hold a position".
- `StrokeStanding` and `StandingRow` gain `ranked` and `holesOwed`; `rank` is 0
  where `ranked` is false, so a reader that forgets to check cannot present a
  place that was never awarded.
- Every reader that used `thru > 0` as a proxy for "has a position" now asks
  `ranked`: qualification, the round cut, the highlights, the foursomes draw
  ("leaders out last"), `positionLabel` (two unranked rows were about to be
  told they were "T0"). `thru > 0` survives where it means "is there a card to
  show", which is a different question.
- The boards say why, on the page rather than in a `title` — the tooltip guard
  exists for exactly that. `LeaderboardTable` captions the row "Not ranked — 50
  of 54 holes played"; `PlayerLeaderboard` reads "thru 14 · not ranked".

### 3. Format-declared input, with an override — DONE

- `GolfFormat.inputs` declares what a format asks to be RECORDED, natural input
  first, beside `sideSize` and `allowance`. Absent means `["gross-cards"]`, so
  most formats say nothing. `inputChoices` puts a card back if a format ever
  leaves it out — "opt out, not opt in" made structural rather than documented.
- Match Play declares `["hole-results", "gross-cards", "match-result"]`.
  **Nassau was found wrong on the way**: `entryModesFor` hard-coded
  `format === "Match Play"`, so Nassau — which `playNassau` resolves from HOLE
  RESULTS — was offered only a gross card. It now declares
  `["hole-results", "gross-cards"]`, and deliberately not `match-result`: "3&2"
  cannot say who took the front nine, so two of the three bets would be invented.
- `Stage.scoreInput` (migration 44, one additive `ALTER TABLE` — the generated
  SQL was read first and carried no drift). `""` means "use what the format
  declares", the same reading `handicapAllowance = 0` already has.
- `resolveScoreInput(format, override)` ignores an override the format does not
  offer. A `"use server"` export is a public HTTP endpoint and its argument
  types are erased at runtime, so "final result only" on a Stableford round has
  to resolve to something an engine can read.
- Wired: a control on the round (only where the format offers a choice),
  `setStageScoreInput`, and `defaultEntryMode` in the entry screen, where the
  committee's decision now beats the net-off-a-card default.

### What OPENING THE PAGE caught, that nothing else did

The handover says almost every real defect this month was found by opening a
page. Three more, and none of the 2318 tests had anything to say about them.

I cannot sign in, so I built a throwaway public event — `zz-look`, invented
names, `@example.invalid` addresses — and read `/live/<token>`, which needs no
session. Deleted afterwards; `zz-` rows left in the dev database: zero.

1. **The Live/Final badge started lying.** `/live` computed
   `allIn = started.every(r => r.thru >= holeCount)`. For a match-play event
   every row's `thru` used to be 0, so `started` was empty and the badge was
   always "Live". With cards joined, one returned card of eighteen holes makes
   `allIn` true — the board would have said FINAL with five matches still out.
   Exactly the hazard the spec names: a hole-count reader that was silent about
   match rounds becomes wrong about them. Now a round WITH MATCHES is finished
   when its matches are settled (`matchSettled`, the reading the rest of the app
   already uses), and a round of returned cards when the cards are in.
   Confirmed both ways on the page: FINAL with all six settled, LIVE with one
   left out.
2. **"F" was measured against the wrong number.** The board read
   "Flight 1 · F · not ranked" for a player who had played 50 of 54 — because
   `holes` is the ROUND's hole count and a round robin puts three matches in one
   round. Now measured against the row's own `holesOwed`, and it reads
   "thru 50 · not ranked". Same fix on `/me`, which had the same assumption.
3. **`resolveSingleMatch` was seeded off `thru > 0`.** A play-off drawn "from
   the standings" would have seeded an unranked card at rank 0 — the top of the
   list. Now `ranked`.

The board as it now reads, on a stroke-format event carrying match cards:
Cassidy and Devon share 1st on complete 54-hole cards; Ainsley and Brody, whose
match ended 5&4, are shown at "thru 50 · not ranked" with their scores still
visible and a dash where the position would be.

### What was NOT decided, on purpose

- **`matchSettled` is untouched.** The spec flags whether it should become "has
  a winner" as a real open question. The card reader uses the stricter test
  locally; nothing about rounds, brackets or money consults it, so the question
  is still open rather than answered by accident.
- **An unreturned stroke card at the end of a completed event.** Rule 3.3b makes
  that an NR, and the app currently ranks it on what was returned. `finished` is
  set only for match-derived cards, so ordinary stroke play behaves exactly as
  before. Deciding NR handling is a separate call.
- **Skins on a match round still read `Scorecard` only.** `skinsPotFor` does not
  see match cards, so a skins pot on a match-play round has no cards to work
  from. Out of scope here and worth its own decision — a pot is a league-round
  feature and nobody has asked for it on a knockout.

## Step 4 — the leaderboard choice. NOT built, and it is Ajay's call

The spec sequences it last and says the polish is "parked on
`claude/tour-leaderboard`". That branch has since merged: e3cba39, "Make the
stroke leaderboard read like a tour board", is an ancestor of `main`. So the
polish has landed and there is nothing to bring over.

What has NOT been answered is the question that started all this — **points, or
a tour-style to-par board, and whose choice is it?** The spec dissolved the
blocker rather than the question: a match-play event now carries real strokes,
so a to-par board there would no longer be a column of zeros. Whether a club
gets that board, and whether the club or the app decides, is a product decision
nobody has made, and building one would be making it.

Where it stands today, with the join in: a match-play event is still ranked on
match points on every screen, exactly as before. `standingRows` now carries the
gross, net, to-par and thru beside those points instead of four zeros, so
whichever way the choice goes, the data is there for it.
