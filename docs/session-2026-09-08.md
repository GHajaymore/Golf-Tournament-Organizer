## Walking the complaint that started this

The original report was that setting up a simple two-player match was
confusing enough to give up on. That had been treated as a UI problem in
general. It is worth writing down what walking it actually found, because the
evidence was sitting in the development database the whole time.

**Two abandoned draft events, five minutes apart.** Both with ZERO players.
Both with their round left on the default Round Robin — one Stroke Play, one
Match Play — and the second carrying the round-robin help text, *"Every player
meets every other in their group."*, as its description. Somebody who wanted
one match against one person built a tournament twice and stopped.

**And the thing they wanted already existed.** `/match/new` — its own comment
says "two people, one round, one screen" — was linked from exactly ONE place,
`/choose`. But:

```
src/app/page.tsx:671
if (session) redirect(session.eventId ? landingScreenFor(session.viewRole) : "/choose");
```

Once an active event exists you never see `/choose` again. The only remaining
door was the ORG onboarding checklist row, which disappears at 3 of 3. The
screen a returning organizer actually uses to create things is `/event`, whose
six templates are all tournaments.

The lesson is not "add a link". It is that **a feature reachable from one
screen is reachable from none as soon as that screen stops being on the way.**
Worth asking of anything added out at the edges: what puts a returning user in
front of it next month?

### The card that was a column

Found while adding that link. `design-system.css` opens `.card` with
`display: flex; flex-direction: column`, so an element carrying `className="card"`
that then sets `display: "flex"` inline has changed NOTHING — it set the
display the card already had, and the column survives.

Four sites meant a row and drew a centred stack. Measured with
`getComputedStyle`, not inferred:

| where | before | after |
|---|---|---|
| `/choose` tournament button | column, 107px | row, 70px |
| `/choose` "Playing a match?" | column, 176px | row, 114px |
| `/event` the new link | column | row, 111px |
| `/me/rules` every rule link | column | row |

The `/choose` pair had shipped that way the day before. Every tell was in the
source and unreadable as a symptom: `justifyContent: "space-between"`
distributing children *vertically*, `marginLeft: "auto"` doing nothing at all,
`textAlign: "left"` quietly overruled by `alignItems: "center"`.
`card-row-direction.test.ts` sweeps for it and asserts its own premise, so it
retires honestly if `.card` ever stops being a column.

### Two players called Dave

Then the match card itself, and this one is not cosmetic. Measured before
anything was changed:

```
parseResultTranscript("Dave wins 3 and 2", "Dave", "Dave")     -> winner "A"
parseHolesTranscript("Dave, half, Dave", "Dave", "Dave", 0, 18) -> [A, H, A]
```

The first records the OTHER Dave as having won the match. The second credits A
with every hole B won. Neither reports anything — the scorer sees a filled card
and a result — and it feeds match points and standings.

`match.ts` already carried a comment about this class, from the fix for "Sam"
matching inside "Samantha": *between two named people that is not a parsing
quirk, it is the wrong result on the board.* This is the case that fix did not
cover, and the worse one: a prefix collision needs an unlucky pair of names,
this needs only two Daves, which any society has.

The rule adopted: **a name that cannot identify anybody is not evidence.** The
result parser leaves the winner null and still reads the margin ("3 and 2"
means the same whoever said it). The holes parser returns `[]` rather than
parsing part of it — dropping only the names from "Dave, half, Dave" leaves
`["H"]` applied to hole ONE, the hole Dave won, with everything after it
shifted up, and a silent misalignment is worse than a refusal. On screen,
`distinctLabels` widens only the names that clash and only as far as it takes.

Swept to every screen showing those names together: the legend, the result
line, the gross-scoring table where strokes are typed, the fourball card where
one person scores for the whole group, and the two ranked lists that mark who
is Advancing.

## The defects that kept recurring

### One reader has the rule; its sibling does not

Seven instances, every one invisible to tsc, the unit suite and the build,
because each screen renders correctly *on its own*. Only comparing two readers
of the same data shows it.

- the treasurer's ledger said "7 shares"; the player's said "$287.00 ÷ 7" (#183)
- the cut line was explained on `(app)/leaderboard` and on neither board a
  player or spectator reads (#185)
- `/live` never passed `unit`, so a spectator saw bare numbers (#187)
- `removeSettlement` was fully authorized, audit-tested, and called by no
  screen at all (#184)
- the settled-payments list existed for players and not for the collector (#184)
- the week sheet asked "has this been played" the stroke way only (#190)
- the public board asked whether every card was in and never asked the
  committee, so a tournament marked Completed still read LIVE (#192)

`ConfirmButton`, `RoundPicker`, `splitLabel` and `cutLineNote` exist to make the
answer shared rather than restated. Prefer that shape: a fragment that cannot be
told where it is — `RoundPicker` reads `usePathname()` — cannot be told wrongly.

**Swept and clean, 2026-09-08:** every component rendered from more than one
page, comparing the props each site passes. No remaining mismatch that was not
deliberate — `youId` is rightly player-only, `canEdit` is organization-mode
only, `shareToken` and `rounds` are tournament-only.

### Cards versus matches

`thru` counts holes on a returned **card**. A match round keeps its results on
the matches, so `thru` is nought for everybody in one, and anything reading
`thru > 0` as "has played" is blind to every match-play event.

Closed everywhere as of #190:

| where | how it asks |
|---|---|
| `standingRows` stroke | `started: s.thru > 0` |
| `standingRows` match | `started: r.stats.played > 0` |
| `live-board` Final/Live | `roundMatches.every(matchSettled)` |
| `week-view` empty + strip dot | `matchSettled` for match, cards for stroke |

The two remaining `thru > 0` filters in `week-view` sit after its
`!state.isStroke` early return and are correctly stroke-only.

#190 is the one worth reading: `empty` blanked the entire week screen,
including the season table beneath it, which had a match branch and the points
all along. The section that could answer the question was hidden by the one
that could not.

### A third: history recomputed from a live record

#195 is the one with teeth. `Event.courseId` is SET NULL, so deleting a club
course preserved the ROWS of every tournament played on it and lost the CARD —
18 pars before, 0 after. The strokes survived and every number derived from
them was wrong: to-par against nothing, handicap allocation with no stroke
index. Both the action's comment and the button said "rounds and matches played
here keep their results", and #180 had promoted that sentence from a tooltip
into prominent visible text.

The fix is the rule this codebase already applies to `Player.handicap`: a venue
is a live record, the card a round was scored against is history. Snapshot it
before the reference goes.

#197 is the same fault one level down and WORSE. A round in a rotating league
carries its own venue, and a `Stage` has no card fields to snapshot into — so
`courseForRound` falls back to the EVENT's course and re-scores that round
against a DIFFERENT one. Measured: par 5 / stroke index 10 before, par 4 /
stroke index 1 after. A missing card is visibly wrong; a different course's
card is plausible and silent, and the stroke index decides which holes a
player's frozen shots fall on, so skins recompute against it.

Refused where the round has cards, allowed where it does not, and the refusal
names the round. The fuller fix — card fields on `Stage` — is a migration
against a branch that auto-deploys, so it is recorded and not attempted.

### Every SetNull relation, swept 2026-09-08

Thirteen of them. Two were broken, and the rest are safe for reasons worth not
re-deriving:

| relation | verdict |
|---|---|
| `Event.courseId` | **was broken** — #195 snapshots the card first |
| `Stage.courseId` | **was broken** — #197 refuses when the round has cards |
| `Match.courseId` | safe: per-hole winners are DERIVED AT SAVE and stored in `Match.holes`, so a later delete cannot move them |
| `Player.teeId`, `Group.teeId` | safe: `RoundHandicap.frozen` holds what each round was scored against, and `resolveRoundHandicap` returns it first |
| `Organization.defaultCourseId` | safe: a default for future events; existing ones are deliberately untouched |
| `Player.memberId` | safe: `deleteMember` is disabled for anyone with entries |
| `Event.seriesId`, `Player.groupId`, flight captains | live associations, no history derived from them |

The pattern that separates the two columns is the whole lesson: **a decision
that was WRITTEN DOWN survives; a number RECOMPUTED from a live record does
not.** Frozen handicaps and stored match holes are safe by construction. The
course card was the one input still being read live at display time.

## What the demo cannot show you

The richest finds came from putting a screen in a state the seed data is never
in. Recorded because the same blindness will recur.

- **Announcements had zero posts** — and so did `e2e/fixture.mjs`, so the
  on-course touch sweep had only ever measured an empty page. The fixture seeds
  two now, one pinned, because pinned and unpinned draw different controls.
- **Demo Cup had zero settlements**, so "Already settled" could not render on
  either money screen.
- **All six demo expenses have the same player on them**, so the data cannot
  distinguish "shows every bill" from "shows only mine". #182 asserts it
  instead of inferring it from an absent filter.
- **Every event in the dev database is match play.** That is what hid #190.
- **No two players ever share a first name.** That is what hid #202 — every
  fixture, every seed and every e2e name is distinct, so the screen could not
  be put in the state where its labels stop identifying anybody. Setting up
  one match with two players called Zz was enough to show it.

And the opposite, worth naming because it is rarer: **the abandoned events in
the dev database were the best evidence in it.** Two drafts with no players,
five minutes apart, said exactly where somebody gave up and what they had
tried. Read what is already there before seeding something new.

## Uploading a club logo, and paying for it twice

Asked for directly: an upload beside the logo URL, with the accepted file
types stated.

The field had only ever taken a URL and the schema said why — *"a URL rather
than an upload because file uploads need blob storage"* — which is true of
storing a FILE and not of a club logo. It is tens of kilobytes and already has
a column. So an uploaded image is resized in the browser to a 512px longest
edge and stored in `Organization.logoUrl` as a `data:` URI. Every reader is a
plain `<img src>` (`OrgBrand` says outright that `next/image` is avoided here
because it would need configured domains), so nothing downstream changed. No
bucket, no route to write, no migration against a branch that auto-deploys.

The size and type rules live in `domain/logo-upload.ts` and are enforced in
`saveOrganizationBranding`, not in the browser that did the resizing —
CLAUDE.md is explicit that a `"use server"` export is a public HTTP endpoint
called with whatever the caller likes. SVG is deliberately not uploadable: it
does not survive the canvas downscale and is markup rather than pixels. It
still works through the URL field, and the help text says so.

### Then the part worth remembering

**#207 is the interesting half, and it only exists because the cost was
measured after shipping #206 rather than assumed away.**

The public board polls every 30 seconds — that is what `LiveRefresh` is for —
and `router.refresh()` re-fetches the rendered payload. A data URI is PART of
that payload, so it went out again on every poll, where a URL is a short
string whose image the browser caches once. Measured on the console
leaderboard with a 40KB logo:

```
URL logo    247,246 bytes
data URI    330,552 bytes      +81KB per render
```

81KB for a 40KB image, because the string lands in both the HTML and the RSC
flight data. At one poll every 30 seconds that is roughly **10MB an hour per
spectator**, on a phone on a golf course — the exact constrained case
`LiveRefresh`'s own comment is about.

So the bytes stay in the column and are served from `/api/logo/<org>`, cached
immutably against a fingerprint of the content. Converted in `brandForEvent`,
where the brand is built, so no screen has to remember.

The general lesson: **"it needs no new infrastructure" is a claim about
storage, not about transfer.** The cheap place to put something and the cheap
way to serve it are different questions, and a page that reloads itself every
thirty seconds turns any inlined byte into a subscription.

## Found, measured, and deliberately not changed

### Two emailless Daves become one club member

`/match/new` is pitched as needing nothing — *"Just the two names. Nobody needs
an account to be played against."* — and both players are then written to the
organizer's club roster through `upsertMember`, which matches like this:

- **with an email** → match on the email
- **without one** → match on the NAME, case-insensitively

Measured against a throwaway club rather than reasoned about:

```
upsertMember(org, { name: "Dave", handicap: 12 })   ->  member X
upsertMember(org, { name: "Dave", handicap: 28 })   ->  member X   (same row)
  members: 1  ·  stored handicap: 28

control, distinct emails, same name                 ->  two rows
```

So an organizer who plays a casual Sunday match against one Dave and a later
one against a different Dave has ONE roster member, and the second man's index
has overwritten the first man's. That index is what a future match or
tournament resolves for "Dave".

**Not fixed, on purpose.** The name fallback is load-bearing: it is what stops
the same emailless person being duplicated every time they are entered, and
removing it would fill the roster with duplicates — the common case — to
prevent an uncommon one. The obvious narrower fix, "don't write the handicap on
a name-only match", refuses a real and frequent action: an organizer
re-entering an emailless member with an updated index. That is the shape
CLAUDE.md warns about in the course-card section — a guard that refuses a real
golf course is worse than no guard — so it wants a decision, not a 6am patch.

The cheap part, if only one thing is done: `/match/new` never says that the
opponent joins the club roster. The registration screen says it in as many
words ("Anyone added here joins the club roster too"), and the match screen —
the one that actively tells you no account is needed — does not. Somebody told
that their opponent becomes a club member would type the email.

Also worth knowing: this is the same identity-collision family as #202, one
layer down. #202 was two Daves inside one match; this is two Daves across
months, in the roster.

## Verification lessons, now in CLAUDE.md

Three of this session's own checks were false and none failed loudly:

- a `node -e` string replace against a CRLF file matches nothing, writes the
  file back unchanged and exits 0 — so a mutation that never applied reads as
  "the test cannot catch this" (#188)
- navigating to an already-visited URL serves it from cache, so `innerText`
  shows the render from before the edit; `/live` has a second, server-side board
  cache on top of that (#189)
- `npm run smoke` is one of the **four** scripts CI's smoke step runs, and the
  other three pin user-facing strings verbatim

What they share is a check that appears to have run and did not, which is worse
than no check. The guard shipped in #178 reported green over four live one-tap
deletes for exactly that reason; #180 is the correction, and it derives its list
from `src/app/actions` rather than restating one.

**And one near-miss with no PR:** writing this handoff nearly destroyed
`docs/session-2026-09-07.md`, by creating a file of that name without checking
whether one existed. It did — 402 lines covering #145 to #155. Caught only
because `git status` said `M` and not `??`. Look at the target before writing
to it; the tools that overwrite do not ask.

### Four more, from the later half

Each of these was a check that looked like it had run, or a fix that looked
like it had landed. None failed loudly.

- **A bulk replace hit a line it was not meant to.** Rewriting
  `firstName(active.aName)` to `aLabel` across `ScoreEntryClient` also rewrote
  the guard `canHearNames`, which then compared the WIDENED labels — and those
  are built to differ, so the guard answered yes every time and switched
  itself off. Every test still passed. Caught only by opening the screen and
  seeing a voice button that should not have been there. **Verify a bulk edit
  by reading the sites it changed, not by counting them** — I checked the
  counts and they were right.

- **`git checkout --` on a file whose real changes were UNCOMMITTED.** Done to
  undo a deliberate mutation, it discarded the work instead. CLAUDE.md already
  says commit before mutating; the reason it says so is this exact sequence,
  and knowing the rule was not enough to follow it under momentum.

- **A test that read a stylesheet raw.** `source-guard.test.ts` caught it the
  day the file was added: assertions made against text that still had its
  comments, on a rule whose own comment names it. The sweep is per file, so a
  new test file is covered immediately — which is the whole point of sweeping
  rather than listing.

- **A fix that reformatted rows it had no business touching.**
  `distinctLabels` defaulted to `firstName`, so using it on a `shortName`
  screen shortened every name there — thirty-one rows changed to fix a
  collision in two. `render.test.tsx` caught it by pinning "A. J.". **A
  display helper takes the caller's format; it does not impose its own.**

Two of the four were caught by guards this codebase already had, one by
looking at the screen, and one by a test written for an unrelated reason. None
by the diff.
