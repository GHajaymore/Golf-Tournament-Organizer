## The two defects that kept recurring

### One reader has the rule; its sibling does not

Seven instances, every one invisible to tsc, the unit suite and the build,
because each screen renders correctly *on its own*. Only comparing two readers
of the same data shows it.

- the treasurer's ledger said "7 shares"; the player's said "$287.00 ÷ 7" (#183)
- the cut line was explained on `(app)/leaderboard` and on neither board a
  player or spectator reads (#185)
- `/live` never passed `unit`, so a spectator saw bare numbers (#187)
- `removeSettlement` was fully authorized, audit-tested, and called by no
  screen at all (#184)
- the settled-payments list existed for players and not for the collector (#184)
- the week sheet asked "has this been played" the stroke way only (#190)
- the public board asked whether every card was in and never asked the
  committee, so a tournament marked Completed still read LIVE (#192)

`ConfirmButton`, `RoundPicker`, `splitLabel` and `cutLineNote` exist to make the
answer shared rather than restated. Prefer that shape: a fragment that cannot be
told where it is — `RoundPicker` reads `usePathname()` — cannot be told wrongly.

**Swept and clean, 2026-09-08:** every component rendered from more than one
page, comparing the props each site passes. No remaining mismatch that was not
deliberate — `youId` is rightly player-only, `canEdit` is organization-mode
only, `shareToken` and `rounds` are tournament-only.

### Cards versus matches

`thru` counts holes on a returned **card**. A match round keeps its results on
the matches, so `thru` is nought for everybody in one, and anything reading
`thru > 0` as "has played" is blind to every match-play event.

Closed everywhere as of #190:

| where | how it asks |
|---|---|
| `standingRows` stroke | `started: s.thru > 0` |
| `standingRows` match | `started: r.stats.played > 0` |
| `live-board` Final/Live | `roundMatches.every(matchSettled)` |
| `week-view` empty + strip dot | `matchSettled` for match, cards for stroke |

The two remaining `thru > 0` filters in `week-view` sit after its
`!state.isStroke` early return and are correctly stroke-only.

#190 is the one worth reading: `empty` blanked the entire week screen,
including the season table beneath it, which had a match branch and the points
all along. The section that could answer the question was hidden by the one
that could not.

## What the demo cannot show you

The richest finds came from putting a screen in a state the seed data is never
in. Recorded because the same blindness will recur.

- **Announcements had zero posts** — and so did `e2e/fixture.mjs`, so the
  on-course touch sweep had only ever measured an empty page. The fixture seeds
  two now, one pinned, because pinned and unpinned draw different controls.
- **Demo Cup had zero settlements**, so "Already settled" could not render on
  either money screen.
- **All six demo expenses have the same player on them**, so the data cannot
  distinguish "shows every bill" from "shows only mine". #182 asserts it
  instead of inferring it from an absent filter.
- **Every event in the dev database is match play.** That is what hid #190.

  their card clears the queue" can spend 30 seconds clicking a "Use theirs"
  button Playwright has already resolved. Seen only on the Windows dev machine,
  never in CI, and it reproduces after a branch switch — which forces a rebuild,
  because Playwright's `webServer` runs `next start`. The button is FOUND and
  the click never completes, so it reads as an actionability wait rather than a
  missing element. #193 fixed the *other* flake in that file and deliberately
  left this one alone.

## Verification lessons, now in CLAUDE.md

Three of this session's own checks were false and none failed loudly:

- a `node -e` string replace against a CRLF file matches nothing, writes the
  file back unchanged and exits 0 — so a mutation that never applied reads as
  "the test cannot catch this" (#188)
- navigating to an already-visited URL serves it from cache, so `innerText`
  shows the render from before the edit; `/live` has a second, server-side board
  cache on top of that (#189)
- `npm run smoke` is one of the **four** scripts CI's smoke step runs, and the
  other three pin user-facing strings verbatim

What they share is a check that appears to have run and did not, which is worse
than no check. The guard shipped in #178 reported green over four live one-tap
deletes for exactly that reason; #180 is the correction, and it derives its list
from `src/app/actions` rather than restating one.

**And one near-miss with no PR:** writing this handoff nearly destroyed
`docs/session-2026-09-07.md`, by creating a file of that name without checking
whether one existed. It did — 402 lines covering #145 to #155. Caught only
because `git status` said `M` and not `??`. Look at the target before writing
to it; the tools that overwrite do not ask.
