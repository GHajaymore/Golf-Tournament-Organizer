## IN FLIGHT: per-round handicap override

The current task. `docs/requirement-per-round-handicap.md` is the requirement;
its five open questions are now ANSWERED — do not re-litigate them.

### Decisions (settled with Ajay, 2026-08-22)

1. **A round's handicap freezes at its FIRST RETURNED CARD.** Not at round
   creation (rounds are made weeks ahead and a wrong roster handicap should
   just be fixable), not at completion (ten cards would already be scored
   against a moving number), not on a button (CLAUDE.md rule 5 — a guard you
   must remember to press is one that will be forgotten).
2. **Resolution order: `frozen` > `override` > `member`.** Frozen beats a later
   override deliberately: an organizer changing an override after cards are in
   has changed their mind, and a played round is not something anyone gets to
   change their mind about.
3. **The override is scoped to ONE round**, with a one-click "apply to the
   remaining rounds" that writes the same value onto each of them as its own
   independent fact. Nothing is inherited.
4. **Consequence Ajay was told about and accepted:** a round holding an explicit
   override does NOT pick up a later member-handicap change. An override is a
   deliberate decision and a roster edit should not silently undo it. If this
   is ever reversed it is a one-line change to the resolution order.
5. **No second lock concept.** The freeze IS the lock for handicaps.
   `isSetupLocked` continues to govern round settings, including the allowance.
6. **The override resolves at COURSE HANDICAP level**, not Playing Handicap, so
   the round's allowance still applies on top. Same unit throughout — this is
   what prevents the defect the 2026-08-12 audit found, where one screen priced
   a card off an index and another off a Course Handicap, five shots apart.

Ajay's own statement of the requirement, worth keeping verbatim:

> "If the round is complete and the member handicap changes on the Member
> screen, the closed round should not be affected and should keep the old
> handicap — but as soon as the member gets a new handicap assigned (or their
> GHIN changes), the next round should use the new one."

### Next: the schema (step 1, still owed)

Follow **`model Scorecard`** exactly — it is the same shape (a row per round per
player) and copying it keeps one pattern:

```prisma
model RoundHandicap {
  id       String @id @default(cuid())
  eventId  String
  stageId  String
  playerId String

  /** The committee's decision for this round, set before play. Null = none. */
  override Int?
  /** What this round was actually scored against. Written once, at the first
   *  returned card, and never rewritten. */
  frozen   Int?
  frozenAt DateTime?

  event Event @relation(fields: [eventId], references: [id], onDelete: Cascade)

  @@unique([stageId, playerId])
  @@index([eventId])
}
```

Then:

```bash
npx prisma migrate dev --create-only --name 46_round_handicap
```

**READ THE GENERATED SQL BEFORE APPLYING.** Prisma emits everything it considers
drift and an unrelated `DROP DEFAULT` can ride along. `45_course_catalog` came
out clean (one CREATE TABLE, two indexes) and was checked; do the same. Rename
the folder to `46_round_handicap` to match house convention before
`prisma migrate deploy`.

### Then step 3 — the freeze

When a round's first card is saved, write `frozen` for **every player in that
round** using `handicapToFreeze`, skipping any row that already has one. This is
the step where a mistake writes wrong handicaps into history rather than merely
displaying one. Add cells to `src/lib/__tests__/matrix.test.ts` per CLAUDE.md,
field sizes from ONE.

### Then step 4 — the screen

Round configuration (`StagesClient`). The override control, "apply to the rest
of the tournament", and — when a round is frozen — say so and show
`differsFromCurrent`, which exists precisely so a player asking "why is my net
different in round one" gets an answer instead of somebody re-entering the
round.

## Two traps this session hit twice each

1. **The shell mangles source edits.** Backticks in a bash heredoc get executed
   (ate two doc references), and writing files as latin1 injected a control
   byte into `ScorecardTable.tsx`. **Use the Edit tool for source edits**, as
   CLAUDE.md already says. `no-control-bytes.test.ts` now sweeps `src/` and will
   catch the byte, but not the eaten backtick.
2. **A quota is not a fact about the world.** The importer recorded an exhausted
   allowance as "374 courses unreadable" and, on the listing endpoint, as
   "Indiana has no golf courses". Both now stop the run loudly. Watch for this
   shape anywhere a failed fetch becomes stored data.
