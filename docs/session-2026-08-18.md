## 2. The backfill — command confirmed against the source

`scripts/backfill-org-owners.ts` opens a plain `PrismaClient`, so it reads the
datasource's `url`, which `prisma/schema.prisma:25` binds to
`PRISMA_DATABASE_URL`. (`directUrl` is `DATABASE_URL`, used only by

## 3. The `kind` disagreement — what the source actually says

Facts gathered before putting the decision to Ajay:

- **Nothing writes a kind other than `personal` today.**
  `services/organization.ts:68` hard-codes `kind: "personal"` on creation, and
  there is no picker anywhere. `club` exists only on rows created by hand or by
  test fixtures.
- **`course` carries no behaviour that `club` does not.** Comparing the two
  profiles in `org-profile.ts`: `sharedRoster` true/true, `ledger` false/false,
  `seasonPlay` true/true, `ownsCourse` true/true, `tracksCash` false/false.
  Every one of the five flags is identical. `course` is a *label*, not a kind.
- **`community` is the one that earns its place.** It is the only combination
  of `sharedRoster: true` with `ledger: true` — a society with a standing
  membership that also splits the minibus. Neither `club` (no ledger) nor
  `personal` (no shared roster) can express it, and the whole money model rests
  on that distinction.
- **Three places still compare the string rather than asking the profile**, and
  all three would get `course` and `community` wrong today:
  - `app/(app)/roster/page.tsx:48` — `isClub={org.kind === "club"}`, where the
    question it is really asking is `sharedRoster`.
  - `components/OrganizationClient.tsx:83,86` — renders "Club" or "Personal"
    and nothing else, so a society would be labelled Personal.
  - `app/choose/page.tsx:127` — shows the org name next to an event only for a
    club.
- One latent oddity worth recording: `services/organization.ts:43` picks a
  membership with `orderBy: { organization: { kind: "asc" } }` to "prefer a real
  club over the personal fallback". That works alphabetically —
  club < community < course < personal — so all three real kinds still sort
  ahead of `personal`. It keeps working by luck, not by design.

Decision put to Ajay. Nothing built until it is answered, because the signup
question writes a kind, the checklist reads it, and the landing page branches
on it.

### Settled: three kinds — `club | community | personal`

Ajay took the recommendation. `org-profile.ts` is authoritative; `course` is
gone; the schema comment now points at it and says so.

`course` was dropped because it answered all five flags exactly as `club` did.
A kind that decides nothing is a question an organizer has to answer for no
reason and a column to fill in every time a flag is added. The word survives in
the signup wording ("A golf club or course"), which is where somebody
recognises their own outfit — it just does not survive as a thing logic asks
about. It cost nothing to remove: no code path writes `kind` at all except the
hard-coded `"personal"` in `services/organization.ts:68`, and a dev-database
count confirmed only `personal` (2) and `club` (1) exist.

The three string comparisons are now `orgProfile()` calls:

- `RosterClient` took `isClub: boolean`, filled in by the page. Now takes
  `orgKind` and asks the profile — a society would have been labelled
  "Personal — your own list of players" while looking at the shared list.
- `OrganizationClient` rendered "Club" or "Personal" and nothing else.
- `choose/page.tsx` showed the org name only for a club; the question it is
  really asking is `sharedRoster`.

## 4. The money game at a club — a real defect, found from Ajay's requirement

Ajay: *"I still want the money game and outing split calculation to occur
within the app… only split for outings or other non-club events. For clubs, it
should still calculate the money game."*

That is what the code INTENDED and not what it did. `me/money/page.tsx` opens
by saying "The pots come first for every kind of organization, because that is
what a player played for" — and then line 42 was `if (mode === "none")
redirect("/me")`. A club resolves to `none` by default. So:

- the organizer could create a skins pot, a 2s pot and a KP, settle them, and
  see the payouts — the prizes screen is gated on the ROUND, not the money
  mode, so it always worked;
- `usesExpenses` returned false, so the Money tab was hidden from players;
- any player arriving by URL was redirected away.

**The money-game calculation was running and nobody it belonged to could see
it.** A pot is a result, not a cash book — which is the very distinction
`org-profile.tracksCash` draws to justify a club having no ledger.

### The fix: two questions, separated

`moneyScreenApplies(mode)` was one flag answering two questions, and the NAME
was the bug — it reads as "show the money screen", so `none` hid everything.

- `sharedCostsApply(mode)` — does the app handle the fees and shared costs?
  The ledger and the kitty. Unchanged behaviour, honest name.
- `moneyScreenApplies({ mode, hasPots })` — does the screen exist at all? True
  when costs are handled in the app OR somebody staked in a pot.
- `hasMoneyGames(eventId)` — the three pot tables `gameNets` settles from
  (`skinsPot`, `sideGame`, `contest`), asked as one question.

`usesExpenses` now gathers facts and does not decide; the rule is pure and in
the domain, so it is tested by the DEFAULT suite rather than only under the
audit config. The pot query is skipped when the mode alone settles it, which
cannot change an OR's answer.

`me/money/page.tsx` now calls `usesExpenses` — the SAME reader the tab uses —
instead of re-deriving `mode === "none"`. A page that redirects while the tab
says it is there is this codebase's oldest bug shape.

Labels corrected, because the fix made them false: `none` was "No money in the
app", which it now plainly is not. It is "Costs handled outside the app", and
the help says the pots are still worked out and shown.

Four tests added to `money-mode.test.ts`, including both directions: a club
with pots gets the screen, a club with none does not (an empty money screen
implies something is missing).

**Verified:** typecheck clean, `next lint` clean (only pre-existing warnings,
none in touched files), production build clean, **2106 unit tests pass** — was

## 5. Two changes from pushing back on the requirement

Ajay asked to be contradicted where there was a better answer. Three were put
to him; he took two.

### The money question is now asked of every kind (taken)

`org-setup.ts` offered the money step only `if (profile.ledger)`, so a club was
never shown it. That turned a DEFAULT into a RESTRICTION: a club can already
set split on one tournament — `resolveMoneyMode` is event → club → kind — but
with nothing on screen mentioning it, nobody would ever find out. A club's
annual away day is an outing, minibus and all; the kind of the tenant does not
tell you the character of the event, which is the whole reason the mode is per
tournament in the first place.

The step is now pushed for every kind, and `done` is
`facts.moneyAnswered || !profile.ledger`. For a club it is **present and
ticked**: the decision genuinely is made, the shop handles it, nothing is
waiting. It is listed so it can be CHANGED, not so it can be nagged about —
`OrgSetupChecklist` renders finished steps as live links and disappears
entirely once everything applies, so a permanently open step nobody must act
on would keep the card on screen forever. A society still gets it genuinely
open, because nothing sensible can be defaulted when the point is who fronted
what.

The club blurb says the pots are worked out regardless — the same distinction
§4 rests on.

### `moneyLayoutFor` deleted (taken)

Imported by nothing but its own test, and encoding a superseded rule: it
decided "does this screen have a ledger?" from the org KIND, which
`resolveMoneyMode` already owns and which it disagreed with the moment a club
set one tournament to split. `me/money/page.tsx` was fixed to stop asking it,
which left it dead but still wrong.

Dead code encoding a superseded rule is not inert — the next person needing
"should this screen show a ledger?" finds a function with exactly that name.
`money-layout.ts` now holds only `roundMoneyIsFinal`, with a note saying what
left and why. Its assertions did not vanish: "round money applies to every
kind" is now `moneyScreenApplies({ mode: "none", hasPots: true })` in
`money-mode.test.ts`, which is the same claim tested where the rule lives.

### NOT taken, and still open

`tracksCash: false` for a club is now false in fact. With the §4 fix a club
player who staked $5 in the skins and won nothing sees **−$5** — the app
telling a member they are down money, which `org-profile.ts:63-79` says it will
never do at a club. The flag conflates POT STAKES (real at a club, settled at
the bar) with SHARED-COST DEBTS (not a club's business) and reads as one.
Nothing is broken today; the comment is what will mislead. Left as Ajay's call.
