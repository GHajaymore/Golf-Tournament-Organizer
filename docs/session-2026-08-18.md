## 3. The `kind` disagreement — what the source actually says

Facts gathered before putting the decision to Ajay:

- **Nothing writes a kind other than `personal` today.**
  `services/organization.ts:68` hard-codes `kind: "personal"` on creation, and
  there is no picker anywhere. `club` exists only on rows created by hand or by
  test fixtures.
- **`course` carries no behaviour that `club` does not.** Comparing the two
  profiles in `org-profile.ts`: `sharedRoster` true/true, `ledger` false/false,
  `seasonPlay` true/true, `ownsCourse` true/true, `tracksCash` false/false.
  Every one of the five flags is identical. `course` is a *label*, not a kind.
- **`community` is the one that earns its place.** It is the only combination
  of `sharedRoster: true` with `ledger: true` — a society with a standing
  membership that also splits the minibus. Neither `club` (no ledger) nor
  `personal` (no shared roster) can express it, and the whole money model rests
  on that distinction.
- **Three places still compare the string rather than asking the profile**, and
  all three would get `course` and `community` wrong today:
  - `app/(app)/roster/page.tsx:48` — `isClub={org.kind === "club"}`, where the
    question it is really asking is `sharedRoster`.
  - `components/OrganizationClient.tsx:83,86` — renders "Club" or "Personal"
    and nothing else, so a society would be labelled Personal.
  - `app/choose/page.tsx:127` — shows the org name next to an event only for a
    club.
- One latent oddity worth recording: `services/organization.ts:43` picks a
  membership with `orderBy: { organization: { kind: "asc" } }` to "prefer a real
  club over the personal fallback". That works alphabetically —
  club < community < course < personal — so all three real kinds still sort
  ahead of `personal`. It keeps working by luck, not by design.

Decision put to Ajay. Nothing built until it is answered, because the signup
question writes a kind, the checklist reads it, and the landing page branches
on it.

## 4. The money game at a club — a real defect, found from Ajay's requirement

Ajay: *"I still want the money game and outing split calculation to occur
within the app… only split for outings or other non-club events. For clubs, it
should still calculate the money game."*

That is what the code INTENDED and not what it did. `me/money/page.tsx` opens
by saying "The pots come first for every kind of organization, because that is
what a player played for" — and then line 42 was `if (mode === "none")
redirect("/me")`. A club resolves to `none` by default. So:

- the organizer could create a skins pot, a 2s pot and a KP, settle them, and
  see the payouts — the prizes screen is gated on the ROUND, not the money
  mode, so it always worked;
- `usesExpenses` returned false, so the Money tab was hidden from players;
- any player arriving by URL was redirected away.

**The money-game calculation was running and nobody it belonged to could see
it.** A pot is a result, not a cash book — which is the very distinction
`org-profile.tracksCash` draws to justify a club having no ledger.

### The fix: two questions, separated

`moneyScreenApplies(mode)` was one flag answering two questions, and the NAME
was the bug — it reads as "show the money screen", so `none` hid everything.

- `sharedCostsApply(mode)` — does the app handle the fees and shared costs?
  The ledger and the kitty. Unchanged behaviour, honest name.
- `moneyScreenApplies({ mode, hasPots })` — does the screen exist at all? True
  when costs are handled in the app OR somebody staked in a pot.
- `hasMoneyGames(eventId)` — the three pot tables `gameNets` settles from
  (`skinsPot`, `sideGame`, `contest`), asked as one question.

`usesExpenses` now gathers facts and does not decide; the rule is pure and in
the domain, so it is tested by the DEFAULT suite rather than only under the
audit config. The pot query is skipped when the mode alone settles it, which
cannot change an OR's answer.

`me/money/page.tsx` now calls `usesExpenses` — the SAME reader the tab uses —
instead of re-deriving `mode === "none"`. A page that redirects while the tab
says it is there is this codebase's oldest bug shape.

Labels corrected, because the fix made them false: `none` was "No money in the
app", which it now plainly is not. It is "Costs handled outside the app", and
the help says the pots are still worked out and shown.

Four tests added to `money-mode.test.ts`, including both directions: a club
with pots gets the screen, a club with none does not (an empty money screen
implies something is missing).

**Verified:** typecheck clean, `next lint` clean (only pre-existing warnings,
none in touched files), production build clean, **2106 unit tests pass** — was
2102, plus the four new ones.

## 5. Two changes from pushing back on the requirement

Ajay asked to be contradicted where there was a better answer. Three were put
to him; he took two.

### The money question is now asked of every kind (taken)

`org-setup.ts` offered the money step only `if (profile.ledger)`, so a club was
never shown it. That turned a DEFAULT into a RESTRICTION: a club can already
set split on one tournament — `resolveMoneyMode` is event → club → kind — but
with nothing on screen mentioning it, nobody would ever find out. A club's
annual away day is an outing, minibus and all; the kind of the tenant does not
tell you the character of the event, which is the whole reason the mode is per
tournament in the first place.

The step is now pushed for every kind, and `done` is
`facts.moneyAnswered || !profile.ledger`. For a club it is **present and
ticked**: the decision genuinely is made, the shop handles it, nothing is
waiting. It is listed so it can be CHANGED, not so it can be nagged about —
`OrgSetupChecklist` renders finished steps as live links and disappears
entirely once everything applies, so a permanently open step nobody must act
on would keep the card on screen forever. A society still gets it genuinely
open, because nothing sensible can be defaulted when the point is who fronted
what.

The club blurb says the pots are worked out regardless — the same distinction
§4 rests on.

### `moneyLayoutFor` deleted (taken)

Imported by nothing but its own test, and encoding a superseded rule: it
decided "does this screen have a ledger?" from the org KIND, which
`resolveMoneyMode` already owns and which it disagreed with the moment a club
set one tournament to split. `me/money/page.tsx` was fixed to stop asking it,
which left it dead but still wrong.

Dead code encoding a superseded rule is not inert — the next person needing
"should this screen show a ledger?" finds a function with exactly that name.
`money-layout.ts` now holds only `roundMoneyIsFinal`, with a note saying what
left and why. Its assertions did not vanish: "round money applies to every
kind" is now `moneyScreenApplies({ mode: "none", hasPots: true })` in
`money-mode.test.ts`, which is the same claim tested where the rule lives.

### `tracksCash` removed (taken, after the fact)

Raised as a documentation problem and turned out to be a duplication problem.

`tracksCash: false` for a club had become false in fact: with the §4 fix a club
player who stakes $5 in the skins and wins nothing sees **−$5**, and an
organizer marks a pot entrant unpaid. The app plainly does track who has paid
at a club.

But rewording it was the wrong fix, because reading the source turned up three
things at once:

1. **Nothing reads it.** The only references outside `org-profile.ts` were its
   own tests and one comment.
2. **It equals `ledger` on every kind** — and a test asserted that identity
   outright ("ties tracking cash to having a ledger"). So it was a second name
   for a rule `ledger` already owns, which is the exact defect class that has
   bitten this codebase repeatedly.
3. Splitting it honestly does not produce two flags. "Does the app count pot
   stakes?" is TRUE for everybody — a constant, not a per-kind question. "Does
   this outfit have shared costs somebody fronted?" is `ledger`. So the honest
   decomposition is a constant plus the flag that already exists.

Removed rather than reworded. The reasoning worth keeping — the shop takes the
entry fee, the professional pays the winner, and a ledger at a club invites a
member to think the club owes them for the buggy — moved onto `ledger`, along
with the distinction the §4 fix rests on: **a stake in a pot is a RESULT,
settled at the bar the same evening; a share of the minibus is a DEBT, and only
some outfits have them.**

`seasonPlay` is also read by nothing, but it is merely unused rather than
untrue, and the season standings and order of merit it describes do exist.
Left alone deliberately — noted here so it is not mistaken for an oversight.

## 6. Onboarding, first increment — and two structural findings

### The front door now creates an organization

`signUp` took name/email/password and created **only a User**. The organization
was created lazily on the first tournament, which left a signed-up organizer
with no tenant at all — and therefore nothing to hang a kind, a name, a plan or
a setup checklist off. That is why "land on Club settings" had no club to land
on.

It now takes a fourth argument, `kind`, and creates the organization.

- **`kind` is validated, not trusted.** A `"use server"` export is a public HTTP
  endpoint and TypeScript types are erased at runtime. An unrecognised kind
  stored here would be resolved by `orgProfile`'s permissive fallback forever
  after, silently giving a club the wrong product.
- **Only when they do not already run one.** Somebody invited as staff has a
  User row and a membership but no password, and claims the account by signing
  up. Creating a second organization for them would leave a junk personal
  tenant beside their real club — and the answer they just gave must not
  restate what their existing club is, the same rule `newOrganizationName`
  follows in never renaming from a later form.
- **One creation path.** `createOrganizationWithOwner` in
  `services/organization.ts` is now the only place an Organization is made, and
  `organizationForNewEvent` calls it too. Three things have to be true of every
  organization and NONE are enforced by the schema: it has a Subscription
  (every limit check assumes one), it has an owner from the moment it exists
  (S1 of the audit was exactly an ownerless club), and its kind is one
  org-profile knows. A second creation site that forgot any of those would be
  invisible until a real club hit it.

The sign-up form asks one new question, as what somebody IS rather than as a
kind, with **no default** — silently answering the most consequential question
in the product is how a society ends up configured as a club:

- A golf club or course
- A society, league or regular group
- A one-off outing with friends

### Finding 1: every link in OrgSetupChecklist was dead

`org-setup.ts` linked to `/settings/organization`, `/courses`, `/members` and
`/tournaments/new`. **Not one of those routes exists.** All five rows were dead
links. Nothing caught it: the component was never mounted, and the render test
asserted the same invented string the code used — the test agreed with the code
and both were wrong.

Real routes are `/organization`, `/event`, `/roster`, `/choose?stay=1`. They now
live in one `SETUP_HREF` table, and a new test **sweeps `src/app` for
`page.tsx`** and asserts every href resolves — stripping route groups the way
Next does. Swept rather than listed, for the reason `e2e/layout.spec.ts` gives
about layout: a hand list covers what its author remembered. A step pointing
nowhere now fails the moment somebody adds it. (Plus a guard that the sweep
found routes at all, so an empty sweep cannot pass it vacuously.)

### Finding 2: this app is EVENT-FIRST, and the requested flow is not

**This is the thing that blocks the rest of the onboarding.**

Every screen in the `(app)` shell goes through `requireScreen` ->
`requireEventSession`, which redirects to `/choose` when there is no active
event. `/organization` additionally resolves its organization *through* the
event: `event.organizationId`.

So an organizer who has just signed up and has no tournament **cannot reach
Club settings at all**, and cannot reach the roster either. The queue's "land on
Club settings, then walk members -> tournament" is inverted relative to how the
app is built: the club settings hang off a tournament, not the other way round.

Nothing here is broken — it is a coherent design, and it is why the org screens
were reached through an event in the first place. But it means the landing and
the checklist mounting cannot be built as specified without one of:

1. **Make the org screens event-free** — `/organization` resolves its org from
   the user's owner/admin membership when there is no active event, with a
   guard that is not `requireEventSession`. Real work, and it touches an
   authorization path, so it wants care rather than speed.
2. **Keep onboarding event-first** — a new organizer lands on `/choose`, which
   already says "Welcome to TourneyHQ / Your account is ready" and already
   carries `CreateFirstTournament`. Mount the checklist THERE. Club settings
   become reachable once the first tournament exists, which is one step in.

(2) is much cheaper and fights the architecture less. (1) is what the original
request described. **Ajay's call — put to him rather than guessed at, because
building the wrong one means building it twice.**

Until it is settled, the checklist correctly says so: for a brand-new
organization the only step that can actually be done is creating the first
tournament, and `SETUP_HREF` carries a note saying why.

Sign-up creates the organization, so every one has a name from birth — the

**"Setting up your personal" and "Name your personal".** Both came from

Overstating a consequence is the same failure as a disabled control with no

## 8. The consequence-point refusal

The honest other half of not gating. `orgSetupState` blocks nothing, because
organizers do not work in order — so where an undone step genuinely stops
something, the control that cannot work has to say so, where it is, with the
way out.

**What was there was worse than a gate.** The Generate flights button read
`disabled={pending || players.length === 0 || locked}` and said NOTHING about
the empty field. A disabled control with no reason is the exact complaint Ajay
raised about Rounds & formats: the organizer cannot tell whether the app is
broken, whether they lack permission, or what to do next.

The locked case had a `title` tooltip, which is not a fix either — it never
appears on a touch device, it is not announced to a screen reader, and it
cannot hold a link. A disabled control with only a tooltip is still a disabled
control with no reason.

`lib/domain/draw-readiness.ts` resolves it, modelled on `resolveThirdPlace`:
return null when the draw can go ahead, otherwise ONE problem in words plus
where to fix it. One at a time and the most fundamental first — somebody told
to add players to a locked tournament does so and is refused again for a new
reason.

**The link goes to `/registration`, not `/roster`,** and the distinction is the
point. The roster is who belongs to the club; the FIELD is who is playing this
tournament, and a draw is made from the field. The handover said "linking to
the roster", which would land somebody one screen short of the thing they need
to do.

A field of ONE draws. Field sizes start at one in this codebase, `formGroups`
already handles it, and refusing here would be a second opinion about a
question that module already answers.
